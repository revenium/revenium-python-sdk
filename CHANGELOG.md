# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.11.0] - 2026-10-23

### Added
- You can now read your team's notify-only per-person budgets (alerts) from the SDK. `revenium_middleware._core.fetch_advisory_budgets()` sends `include=advisory` on `GET /v2/api/ai/enforcement-rules/{teamId}`, which the API serves from 2.25.0, and returns the advisory rows (`source` `ANOMALY`, `action` `NOTIFY`, with a per-person `groupBreakdown` and, when the current window has a reading, `readingAt`), `[]` when the team has none, or `None` when the read could not be completed. Like `fetch_enforcement_rule` it is an inspection call: it neither reads nor writes the cache the pre-call check evaluates, so an advisory budget never blocks a call. The background poller and the stale-cache refresh keep sending the read they always sent, without `include`, because an advisory budget's numeric id can equal a cost limit's and the pre-call check keys its warnings on that id.
- AI completions can now say how the coding assistant that made them was launched. `create_completion` (sync and async) accepts `entrypoint`, and every provider integration that meters completions reads it from `usage_metadata` as `entrypoint`, so coding-assistant spend can be split by launch surface (Claude Code sends `cli`, `sdk-cli`, `sdk-ts`, `sdk-py`, `claude-vscode` or `claude-in-slack`; other values of the same shape are sent as given). A value Revenium refuses (empty, longer than 64 characters, or holding anything but letters, digits, dots, hyphens and underscores) is left off the record with a WARNING and the call is still recorded, since Revenium answers such a record with a 400 and stores none of it. When it is unset it is left off the request, so existing integrations send exactly what they did before. It applies to completions only: passing it on an image, video or audio call changes nothing. The LiteLLM proxy, which takes attribution from `x-revenium-*` headers, does not read it.

### Fixed
- A department cost cap scoped to a provider, model, agent, task type, product, organization or credential no longer blocks the person's other calls. The cap's verdict used to reach the SDK as one rule per person, which the pre-call check applied to every call they made, so a breached cap on OpenAI also refused their Anthropic calls. When the API publishes `departmentBudgetCandidates` for a person (every department cap that could apply to them, best first), the check now takes the first cap whose own filters cover the call, compared without regard to letter case as the cap's total is counted, and blocks or warns on that one alone; a call no candidate covers gets no department verdict. A filter the SDK cannot judge still counts as covering the call, and so does a credential filter on a call that names its credential only by raw value (the cap's total is counted under the credential's saved name), a cap whose window has ended is passed over for the next, and a person the API publishes no list for keeps the single-rule verdict exactly as before. The list is kept in the department snapshot under `REVENIUM_CACHE_DIR`, and a snapshot written by an earlier version still loads.
- An empty `client_surface`, `effort`, `speed`, `prompt_id`, `prompt_length`, `query_source` or `subagent_type` in `usage_metadata` now gets the WARNING promised for a value Revenium refuses, and is left off the record, unless the field's other spelling (`clientSurface` beside `client_surface`, for example) carries a value, which is then sent; before, it was silently treated as unset, so a caller had no sign that the tag was missing. A direct `create_completion` call (sync or async) now runs the same check the provider integrations run before sending: any optional value Revenium would refuse is left off with one WARNING per field (a subscriber id or email included), and a text tag longer than Revenium stores is shortened with a WARNING; before, the value was sent as given and Revenium refused the whole record with a 400, so the call's tokens and cost were never stored.
- The SDK's check that every public provider call is either metered or knowingly left out passes again on anthropic 1.17.0 and openai 3.36. The calls those releases added (Anthropic `user_profiles`, organization `webhooks` and workspace `rate_limits.update`; OpenAI `audio.voice_consents`) manage accounts, settings and consent recordings and never call a model, so the README's "Calls the SDK does not meter" list is unchanged.
- The same check passes again on perplexityai 0.45.0 and later, which added `batches` and `files`. `batches.create` submits a batch job that Perplexity bills as it runs, so the SDK records no usage for it and the README's "Calls the SDK does not meter" list now names it for Perplexity. The other `batches` calls and every `files` call manage jobs and their input files and never call a model.

## [0.10.1] - 2026-10-14

### Changed
- LiteLLM proxy guardrail: a call's Revenium trace id now defaults to the LiteLLM session id the caller sent (the `x-litellm-session-id` or `x-litellm-trace-id` header, or `litellm_session_id` or `metadata.session_id` in the request body, `litellm_metadata.session_id` on `/v1/messages`), so calls grouped into one LiteLLM session read as one trace. `x-revenium-trace-id` still wins, and `x-claude-code-session-id` is now the fallback after the LiteLLM session id, so a call that sends both a LiteLLM session id and `x-claude-code-session-id` now takes the LiteLLM session id as its trace id. The id LiteLLM generates for every request is never used, and neither is a session id LiteLLM generated itself under its `missing_session_id: generate` policy, so a call that names no session still has no trace id. The deprecated callback is unchanged.

## [0.10.0] - 2026-10-13

### Behaviour changes

These can change what your application sees when you upgrade from 0.9.2. Each one is described in full below.

- Default Revenium address: with no address set, the low-level outcome client (`AgenticOutcomeSettings`) and the `examples/agentic_outcomes` pack send usage records and outcomes to `https://api.revenium.ai` instead of `https://api.revenium.io`, and `JobContext`, `get_outcome_history` and the job-type economics functions follow your usage address instead of `https://api.revenium.io`. The entry under Changed says how to keep the old address.
- `AgenticOutcomeClient.emit_completion` and `emit_tool_event` queue the record and return at once, so delivery errors are logged instead of raised. A payload missing a required key still raises `ValueError`.
- `revenium_middleware.webhooks.verify_signature` returns False when the signing secret is passed as plain text. Pass a list, `secrets=[os.environ["WEBHOOK_SECRET"]]`; a tuple still works.
- A failed tool event's `errorMessage` and an automatic FAILED job outcome carry only the exception's class, not its message, unless you set `REVENIUM_CAPTURE_ERROR_MESSAGES=true`.
- Tool events carry a `transactionId` of their own. The `transaction_id` you set is sent as the event's `traceId`, or as `usageMetadata.callerTransactionId` when you also set a `trace_id`, and calling `report_tool_call` twice with identical arguments records two events instead of one.
- `idempotency_key()` and `set_idempotency_key()` raise `ValueError` for a key Revenium cannot accept (it must be 1 to 255 printable ASCII characters, with no leading or trailing spaces), and entering `JobContext` raises `ValueError` for a job id Revenium refuses on AI calls (it must start with a letter or digit, use only ASCII letters, digits, `.`, `_` and `-`, be at most 255 characters, and not be `types` or `conversion-funnel`), before anything in the block runs.
- Google Gemini errors reach your code as google-genai's own exceptions instead of `MeteringError`. Catch `google.genai.errors.APIError` for provider failures.
- Some calls are recorded under a different provider label, so provider breakdowns, provider-scoped spending caps and alerts see them differently:
  - xAI calls through the OpenAI client pointed at `https://api.x.ai/v1`: `XAI`, was `OPENAI`.
  - OpenAI Responses API calls to Perplexity: `PERPLEXITY`, was `OPENAI`.
  - LangChain models metered by the Revenium callback, all previously `OPENAI`: Gemini and Vertex AI `Google`, Bedrock `AWS`, Cohere `COHERE`, Hugging Face `HUGGINGFACE`, Mistral `MISTRAL`, LiteLLM `LITELLM`, Perplexity `PERPLEXITY`, and `ChatAnthropicVertex` `ANTHROPIC`.
  - Gemini and Vertex AI records name their source `PYTHON` instead of `python`.

### Added
- `revenium_middleware.flush_metering(timeout_seconds=None)` sends the usage records queued or held so far and returns how many are still unsent, waiting at most `timeout_seconds` (default `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS`, 5 seconds). Metering carries on afterwards. Call it at the end of a job in a worker that ends with `os._exit`, such as a raw `os.fork()` worker or an RQ work horse; see the README's "Worker processes" section.
- `revenium_middleware.carry_context(fn)` carries a `@revenium_meter` or `@revenium_metadata` function's metering mark and tags into a worker thread. Call it inside the decorated function each time you hand work to a thread, for example `pool.map(carry_context(summarize), docs)`.
- `revenium_middleware.metering_key(api_key, base_url=None)` meters several of your own customers in one process. It is a context manager: the usage records and tool events of the calls made inside it go out under `api_key`, on the current thread or asyncio task only, while other threads and tasks keep their own key. A thread started inside the block does not inherit the key; an asyncio task created inside it does. `base_url` defaults to the address set with `initialize_metering()` or `REVENIUM_METERING_BASE_URL`. An empty or malformed key raises `ValueError`. A key set with `configure(api_key=...)` still wins for tool events, and those events go to the address set with `configure(metering_url=...)`, else the process-wide address, never to the block's `base_url`, where that key is not valid. Without a `configure()` key, tool events in the block go out with the block's key and the block's address together, even when the block sets no `base_url`; `configure(metering_url=...)` alone does not redirect them. Spending caps keep following the process-wide key and `REVENIUM_TEAM_ID`, never a `metering_key()` key, so a service that sets its keys only this way gets no spending caps. Outcomes and jobs are not covered: they need a write key (`rev_sk_`). Every customer key shares one set of connections to Revenium.
- OpenAI speech, transcription and translation calls are metered. `audio.speech.create`, `audio.transcriptions.create` and `audio.translations.create` sent nothing to Revenium, so you paid OpenAI for every Whisper transcription, translation and text-to-speech call while Revenium showed no usage for it; the Go and Node SDKs already recorded them. Each call, sync, async, streamed or through `with_raw_response`, now sends one audio record with the model, the audio duration (or, for token-billed transcription models, the tokens) or the number of characters spoken, and your `usage_metadata` attribution. Audio calls now also respect your spending caps: when a blocking budget rule is breached, the call raises `BudgetExceededError` before it reaches OpenAI, as chat calls do. Transcriptions in `text`, `srt` or `vtt` format, default-format translations and `with_streaming_response` calls report no duration and are recorded with zero seconds, at no cost; see the README's OpenAI Audio section. Calls made before the upgrade are not recovered.
- README: a "Calls the SDK does not meter" section lists the provider calls you pay for that send no usage record to Revenium: OpenAI realtime and Live, legacy `completions.create`, Assistants runs, Decisions and batches; Gemini Interactions, Live and context-cache creation; Perplexity Search; LiteLLM's Anthropic-style messages call, image, speech and video calls; Ollama's `systemone` and web search; fal realtime; the older Vertex AI language and vision models, Vertex AI batch prediction, supervised tuning and context caches; and raw boto3 calls to AWS Bedrock (Claude models are metered there only with `REVENIUM_BEDROCK_TRANSPORT` on). To record one of these calls, wrap it with `@meter_tool`.
- Read jobs back from Python. `list_jobs`, `get_job`, `get_job_types`, `get_job_roi`, `get_job_transactions` and `get_conversion_funnel` return what the Revenium jobs API holds, as the Go and Node SDKs already could, so an agent can check its own return on investment and a script can list finished jobs without hand-written HTTP calls. Like every outcome call they need a write-scope key (`rev_sk_`). `get_job` also returns the job's `entityVersion`, which is what to retry an amendment with when a conflict reports no version.
- `REVENIUM_LITELLM_PIN_ORGANIZATION_TO_KEY_TEAM` (default off) for the LiteLLM gateway. Without it, anyone holding a team's virtual key can send `x-revenium-organization-name` (or the retired `x-revenium-organization-id`) naming another organization, and their calls are then checked against that organization's spending cap and recorded under its name instead of their own team's. Set it to `true` and a key that belongs to a LiteLLM team is always checked and recorded under that team's alias; keys with no team alias still take the organization from the header. The proxy logs at startup when the setting is on, and warns when it is set to a value it does not recognise. See the README's Proxy Mode section.
- `REVENIUM_CAPTURE_ERROR_MESSAGES` (default `false`). When set to `true`, a failed `@meter_tool` call, a `JobContext` block that ends in an exception and a failed OpenAI, Anthropic, LiteLLM, Google (Gemini or Vertex AI), Perplexity or Ollama call send the exception's message to Revenium as `<Class>: <message>`, capped at 2048 characters for a tool event or a job outcome and at 255 characters, HTTP status included, on a failed model call's record, with `[REDACTED]` in place of card numbers, every API key shape prompt capture masks (xAI, Perplexity, AWS, GitHub, Slack, Hugging Face, Google, Revenium and the others, plus `pk-` and `Token` values), JSON Web Tokens, query-string values, bearer and Basic tokens, URL user names and passwords, values under labels ending in a sensitive name, and emails. A label only containing a sensitive word keeps its value, so `SYSTEM-SECRET-INSTRUCTIONS: never` and `max_tokens: 1000` are sent as written. A provider's HTTP error can quote the request, system prompt and user question included, so its message is sent only when `REVENIUM_CAPTURE_PROMPTS` is on as well; otherwise a failed model call sends its class and HTTP status, and a tool or job that a provider error ended sends the class.
- Griptape: `enable_budget_errors()` makes a spending-cap refusal reach your `except BudgetExceededError` block from `agent.run(...)`, `Pipeline.run()` and `Workflow.run()`, in any thread. Griptape turns any error inside a task into an error result, so until now an agent stopped by a cap returned the refusal text as its answer. Call it once at startup; nothing is installed on import. It uses Griptape's observability hook and wraps an observability driver you already set (or pass yours as `delegate=`); inside a `with Observability(...)` or `with GriptapeCloudStructure(observe=True)` block, call it after the block opens, because leaving the block turns it off. `disable_budget_errors()` turns it off. `raise_if_budget_exceeded(agent)` raises the same error after `run_stream` or without the setup line. Griptape still logs each refusal at ERROR and keeps it in conversation memory. Not covered: the LiteLLM gateway route, which reports a cap as HTTP 429 (`requests.HTTPError`), and a refusal inside a tool, which reaches the model as the tool's output.
- AI completions can now say which Claude Code app sent them. `create_completion` (sync and async) accepts `client_surface`, and every provider integration that meters completions reads it from `usage_metadata` as `client_surface` or `clientSurface`, so coding-assistant spend can be split between the terminal CLI (`claude-code`) and the desktop app (`claude-code-desktop`). A value Revenium refuses (empty, longer than 64 characters, or holding anything but letters, digits, dots, hyphens and underscores) is left off the record with a WARNING and the call is still recorded, since Revenium answers such a record with a 400 and stores none of it. When it is unset it is left off the request, so existing integrations send exactly what they did before. It applies to completions only: passing it on an image, video or audio call changes nothing. The LiteLLM proxy, which takes attribution from `x-revenium-*` headers, does not read it.

### Changed
- Failed tool events and auto-failed job outcomes send the exception's class, not its message, unless `REVENIUM_CAPTURE_ERROR_MESSAGES=true`. The message was sent word for word, and Python's HTTP libraries put the whole request URL in it, so a tool calling an API with its key in the URL (Google Maps and many other Google APIs take `?key=`) sent that third-party key to Revenium on every failure, with whatever else the URL or the error carried, even with prompt capture off. A failed `@meter_tool` call now sends, for example, `"errorMessage": "HTTPStatusError"`, and an auto-failed `JobContext` outcome sends the class in `metadata.error` and `outcomeReason` (`metadata.errorType` is unchanged). A tool whose exception cannot be turned into text no longer has that error replace its own exception. Text already stored is not changed. The Go and Node SDKs still send the message.
- Default Revenium address: if you use the low-level outcome client (`AgenticOutcomeSettings`) or the `examples/agentic_outcomes` pack and set no address at all, your usage records and your outcomes now go to `https://api.revenium.ai` instead of `https://api.revenium.io`. If you use `JobContext`, `get_outcome_history` or the job-type economics functions and set no outcome address, those calls now follow your usage address (`REVENIUM_METERING_BASE_URL`, default `https://api.revenium.ai`) instead of going to `https://api.revenium.io`. Nothing changes if you already set `REVENIUM_PROFITSTREAM_BASE_URL` or pass `profitstream_base_url=`. To keep the old address, set `REVENIUM_PROFITSTREAM_BASE_URL=https://api.revenium.io` for outcomes, and for the low-level client pass `meter_base_url="https://api.revenium.io"` or set `REVENIUM_METERING_BASE_URL=https://api.revenium.io`.
- Low-level outcome client: `emit_completion` no longer sends `null` for optional fields you did not set. A payload with only the 13 required fields used to go out with 26 extra fields set to `null`; those fields are now absent from the request. A required field you set to `None` is still sent as `null`.
- LiteLLM 1.105.0's new `systemone` and `asystemone` calls are not metered: they send a Decisions request straight to the model provider, as `decisions` does, so you pay the provider while nothing reaches Revenium. The README's "Calls the SDK does not meter" list now names them.
- Tool metering (`@meter_tool`, `report_tool_call`) reuses one pool of HTTP connections for every tool event and every buffered tool event it replays, as AI usage records already did, instead of opening a new client and connection per event. On one local test host, 200 tool events used 22 connections instead of 200, and 30 tool events a second used 0.12 of a CPU core instead of 0.83 (0.18 instead of 0.98 with 10 AI calls a second added), with every record delivered. Hosts with slower CPUs or a TLS endpoint saved more in the sweep that found this. Tool metering now reads `HTTPS_PROXY`, `NO_PROXY` and `SSL_CERT_FILE` once, at the first tool event, instead of on every event.
- Tool events now carry a transaction id of their own. When you set a `transaction_id` through `context()`, `set_context()` or `report_tool_call()`, each tool event gets its own `transactionId` (a UUID derived from your value, the tool, the operation, the moment the call was made and a per-process sequence number), and your value is sent as the event's `traceId`, or as `usageMetadata.callerTransactionId` when you also set a `trace_id`. A tool event the SDK sends again itself (an HTTP retry or a replay from the delivery buffer) keeps its id and is still stored once. Calling `report_tool_call` twice with identical arguments now records two events; before, every tool event under one transaction id was sent with that id as its `transactionId` and idempotency key, so Revenium kept only the first.
- `AgenticOutcomeClient.emit_completion` no longer sends `agentName` or `currency`. Revenium never stored them, so nothing you had is lost; the agent is `agent`, and a one-time warning about unsent keys names `agentName` and `currency` when a payload carries them. The shipped agentic outcomes examples no longer send them.

### Deprecated
- The `operation_type` argument of `@revenium_meter` is deprecated and ignored. It never changed a record: the operation type is detected from each call, so a chat and an embedding in one function keep their own types. Passing it now logs one warning per process. To label a function's calls, use `metadata={"task_type": "..."}` or a `transaction_name`. The argument still exists, so no code breaks.
- `ReveniumCrewWrapper`'s `organization_id` and `product_id` arguments. Use `organization_name` and `product_name`; the old names keep working for now.

### Fixed
- Gemini answers that think before replying are recorded at what Google bills. Google reports thinking tokens (`thoughts_token_count`) outside the answer's `candidates_token_count` and bills them at the output rate, and the Google AI and Vertex AI integrations sent only the answer tokens as output and `reasoning_token_count` as 0, so a Gemini 2.5 thinking call was priced at a fraction of its cost. Output tokens now include the thinking tokens and `reasoning_token_count` carries the thinking part, as the Go SDK already does: a call Google reports as 61 prompt, 15 candidates and 39 thoughts tokens is recorded as 61 input, 54 output and 39 reasoning. Calls from models that do not think, and google-genai versions without `thoughts_token_count`, are recorded as before. Records sent before the upgrade are not changed.
- Installing the SDK without the `[anthropic]` extra left `wrapt` out, so the Anthropic patch failed to load, one ERROR line was logged and every Claude call went unmetered while `is_initialized()` kept reporting True. `wrapt` is now a base dependency, so `pip install revenium-python-sdk anthropic` meters Claude calls, and `is_initialized()` reports False whenever the patch did not load.
- `revenium_middleware.webhooks.verify_signature` now returns False when the signing secret is passed as plain text instead of a list. Before, each character of the text counted as its own secret, so a webhook forged with any one character of the secret verified. Wrap the secret in a list, as the README example does: `secrets=[os.environ["WEBHOOK_SECRET"]]`. A tuple of secrets still works; any other type (a dict, a number) now returns False instead of raising or trusting the dict's keys.
- A Revenium address routed through your own gateway now keeps its path. With `REVENIUM_METERING_BASE_URL=https://gw.acme.com/metering/revenium` (or `/meters/v9`), usage records go to `https://gw.acme.com/metering/revenium/meter/v2/ai/completions` and tool events to `.../metering/revenium/meter/v2/tool/events`; before, any path containing the text `/meter` was cut to `/meter` at the top of the host. Addresses that already end in `/meter` or `/meter/` are unchanged. If you built a gateway route at the cut path, move it to the full path. A query string or fragment in the address is now dropped with a warning that names the problem but not the value; before, it was pasted into the request path, so it never worked. The outcomes and jobs address derived from the same setting drops it too.
- The startup warning for an invalid `REVENIUM_METERING_BASE_URL` no longer prints a key or password pasted into it. A Revenium key shows as `[REDACTED]`, a user name and password in the address are removed, and any other value is cut to its first 16 characters, enough to recognise a mistake such as a missing `https://`.
- With `REVENIUM_CAPTURE_PROMPTS=true`, LangChain calls the Revenium callback records now store their system prompt, input messages and reply. These are chat models no Revenium client integration meters, such as ChatGroq, ChatMistralAI, ChatCohere, Fireworks, Hugging Face and langchain-google-vertexai models, and text-completion models. Their records carried tokens and cost but no prompt and no reply, with no warning. Sync, async and streamed calls are covered, and a streamed reply is stored joined. The same 50,000-character cap, `prompts_truncated` flag and credential masking apply as on every other path. A text-completion prompt is stored as one `user` message, and tool calls inside the history are not captured. With capture off, or for a call selective metering leaves unmetered, the SDK no longer holds a copy of the prompt while the call runs. ChatOpenAI with the OpenAI integration loaded is still recorded once, by the OpenAI integration.
- Revenium metadata passed to Perplexity as `extra_body={"usage_metadata": ...}` no longer reaches Perplexity on OpenAI-client Responses and embeddings calls or on native search, embeddings, contextualized embeddings, async chat and browser session calls. OpenAI-client Responses calls with it are recorded and capped under that subscriber and organization. The native calls that are not metered now also accept `usage_metadata=` instead of raising `TypeError`.
- A call whose usage record holds a value JSON cannot write is now recorded, on every provider. A subscriber id or organization that is a `UUID`, a `Decimal` quality score, a `date` or `datetime`, `bytes` from Redis or a database driver, a `NaN` or infinite number, a dict that contains itself, or text holding half of an emoji (a lone surrogate, as an emoji split across two stream chunks leaves) made the whole record fail to send: the call was answered and billed by the provider, but Revenium never saw it, so it escaped spend reports and spending caps, and it was not kept for retry. Such a value is now sent as text (a UUID, date or bytes), as a plain number (a `Decimal`, so `Decimal("0.9")` arrives as `0.9`), with the broken character replaced, or left off (NaN, infinity, a self-reference) with one warning that names the field, never its value. An emoji split across stream chunks now reaches the captured reply whole. A plain record is sent exactly as before. A spending cap scoped to one person still does not match a subscriber id passed as a `UUID` object; pass it as text for now. Calls made before the upgrade are not recovered.
- A tool whose recorded output holds a `Decimal`, `date`, `UUID` or `NaN`, a `report_tool_call` whose `usage_metadata` holds one, and a failed tool whose captured error text holds half of an emoji now send their tool event. Before, the event failed to send and was dropped, so the tool's cost never reached Revenium; the only trace was a `metering error: Object of type Decimal is not JSON serializable` line that named neither the tool nor the field. Values are converted as for usage records (a whole `Decimal("8.0")` arrives as `8`), the value your tool returns to its caller is unchanged, and the `metering error` line now names the tool.
- With prompt capture on (`REVENIUM_CAPTURE_PROMPTS=true`), OpenAI Responses API calls now record their instructions, input and reply. They were stored with no prompt and no reply at all, though the README said capture works for OpenAI, and nothing was logged. Every form is covered: `responses.create` and `responses.stream`, sync or async, streamed or not, through `with_raw_response`, and background calls. Chat calls made through `with_raw_response`, which is how every LangChain `ChatOpenAI` call reaches OpenAI, and async streamed chat calls (LangChain's `astream` included) now record the reply too; they kept the question but not the answer. For a Responses call the system prompt is `instructions`, or else the first `system` or `developer` input item. Captured text is masked and truncated as for chat calls, and tokens and cost are unchanged. Async `with_streaming_response` calls that are not streamed are still not recorded; the README's Prompt Capture section lists what is not captured. Calls made before the upgrade are not recovered.
- Spend tagged with a ticket id now counts toward that ticket when it goes through the LiteLLM gateway and when it is a streamed Claude call on Bedrock made with Anthropic's own client. Those records carried the environment and trace type you set but never the ticket, so ticket totals left that spend out. The gateway reads the new `x-revenium-ticket-id` header per call, else `REVENIUM_TICKET_ID` on the gateway host. A ticket id passed as a number (or any other non-string) is now ignored instead of losing the call's whole usage record.
- Gemini chat turns accept `usage_metadata`. `chat.send_message(...)` and `chat.send_message_stream(...)`, on `client.chats` and `client.aio.chats`, raised `TypeError` when given `usage_metadata`, so the README's way of tagging a call crashed a chat turn, and an untagged turn was recorded with no organization, product or agent. The tags now reach that turn's usage record, which is still sent once, and apply to that turn only.
- A LangChain call that is cancelled (a timeout, a dropped request, a stopped agent) or a batched `generate` that fails part way no longer stays in the Revenium callback's memory with its whole prompt. langchain-core sends no end event for such a call, so a long-running async service using `ReveniumCallbackHandler`, `wrap()` or `attach_to()` grew with every cancelled call (2,000 timed-out calls with 20,000-character prompts held about 48 MB in a local test). The callback now sets these calls aside as soon as langchain-core gives up on them and drops their prompts at once; it keeps at most 256 small prompt-free entries per handler, so that a late answer can still be recorded. A call whose answer langchain-core is still delivering when the timeout hits is kept, without its prompt, until that answer arrives, so it is still recorded however many other calls are cancelled in the meantime. Answered calls are recorded exactly as before, and a cancelled or failed call still sends no record.

A trace type or trace name that is not a string (for example `trace_type=5`) is now left off with a WARNING naming its type on every provider; before, it made an OpenAI `chat.completions.create` call raise `TypeError` and was sent as typed on Claude calls.

A blank snake_case key no longer hides a filled camelCase one. Other per-call fields resolved the same way, such as effort or service tier, now leave out a blank value instead of sending `""`. A gateway call's blank job header still has no environment fallback, as the README describes.

A request without the header, or with a blank one, sends the same record as before.
- A job run in its own worker process on Linux now sends its usage records. A `multiprocessing.Process` child started with the fork or forkserver start method (the Linux default) ends without running exit hooks, so the records of its model calls died with it and nothing was logged: 20 jobs of one call each meant 20 paid calls and 0 usage records. The SDK now flushes such a child when its target returns, within `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS`, and logs a warning with the count of any records it could not send. `Pool` workers flush when they exit, not after each task; see the README's "Worker processes" section for the shapes that still need `flush_metering()`.

A forked child shared its parent's metering connections and queue: it could hang on a lock held at the fork and lose every record it made, resend the parent's waiting records under new keys, and corrupt request bodies on a shared socket. A forked child now starts with its own queue, buffer and connections, under the same key and address, and its exit warning counts only its own records.
- A service restarted soon after a Revenium outage now sends the usage it was holding. The exit flush sent held records one at a time, so at a quarter-second round trip a 5 second budget delivered 13 of 500 and dropped the rest. It now sends up to 32 at a time, still within `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS`: 200 held records at a quarter-second round trip all arrive in about 2 seconds. A background catch-up running when the process exits hands over to the exit flush after its current batch. On Python 3.12.0 to 3.12.2, which cannot start threads during exit, the flush still sends one at a time and stops at the budget.

The provider was never called on either attempt. Other provider errors are retried as before, and any `ignored_exception_types` you pass is kept, with `BudgetExceededError` added.

The client's jobs and outcomes follow an address set in code too, unless an outcome address is set with `profitstream_base_url=` or `REVENIUM_PROFITSTREAM_BASE_URL`, or `meter_base_url=` names an address other than the one in `REVENIUM_METERING_BASE_URL`, so a job and its outcome never land on two addresses. When messages do overflow, the longest texts are shortened and `input_messages` stays valid JSON; it could be cut mid-JSON before, so it would not parse.

This is a visible change: `idempotency_key()` and `set_idempotency_key()` now raise `ValueError` for such a key, naming the rule (1 to 255 printable ASCII characters, no leading or trailing spaces), before anything in the block runs. Every Anthropic path now finds the metering client the same way the other integrations do, and a later `initialize_metering()` takes effect on every thread.
- Tool events from `@meter_tool` and `report_tool_call` use the same key and address as your AI records. Three things change: (a) a key passed to `initialize_metering()` now reaches tool events, which were skipped with "no API key configured" when the key was not also in the environment; (b) rewriting `REVENIUM_METERING_API_KEY` in a running process no longer changes the tool-event key on its own; call `initialize_metering()` to switch keys, as AI records already require; (c) a key the SDK rejects as malformed is no longer sent for tool events. A `REVENIUM_METERING_BASE_URL` that does not start with `http://` or `https://` now sends tool events to the default Revenium address, as AI records already did, instead of to an address that could never succeed, which kept them in the buffer for 24 hours. `configure()` values still win over both.
- Records held during a Revenium outage are delivered under the key they were made with. A service that meters work for several of its own customers, switching keys with `initialize_metering()`, sent every held record to whichever key was current when Revenium came back, so one customer's usage could land in another customer's account. A usage record now keeps the key and address that were current when it was queued, which for most non-streamed calls is when the call returned, and a tool event the ones current when the tool started, including records that waited in the delivery queue or overflowed into the buffer; each is delivered under that key even if metering is later switched to another key or turned off. Streamed calls, Veo videos and LangChain callback records keep the key that was current when their call started (see the entry on switching keys while calls are running). Anthropic `messages.with_streaming_response.create()` calls without `stream=True` and Perplexity responses read raw or lazily also keep the key that was current when their call started, even when you read the body after a switch. A held record whose key Revenium rejects (401 or 403) is discarded and counted as a metering error, as a live record with that key would be; it is never resent under the current key. If you rotate a key, keep the old one valid until held records have been delivered.
- fal: a language model call is recorded as a chat completion with the tokens fal reports. Calls to fal's language model endpoints (`fal-ai/any-llm`, `fal-ai/any-llm/enterprise`, the OpenRouter router `openrouter/router`) were each recorded as one generated image with no tokens, because the SDK chose the record type from media keywords in the endpoint name and treated everything else as an image. They are now recorded as chat completions carrying the prompt and completion token counts from the `usage` fal returns, where a reported zero is sent as zero, and the total fal reports, or prompt plus completion when fal reports no total or a total of zero. `openrouter/router/video` and `openrouter/router/audio`, which fal prices by tokens, move from video and audio records to chat completions for the same reason, and so does an endpoint the SDK does not know whose result reports token usage. `fal-ai/any-llm` reports no token usage, so its record is a chat completion with zero tokens. A streamed call is recorded as one streamed completion with the tokens on the final stream event. Image counts for fal drop by the number of language model calls that used to be counted as images. The model on the record is still the fal endpoint, for example `fal_ai/fal-ai/openrouter/router`. Image, video and audio endpoints are recorded as before, including when their results carry `usage`. Calls made before the upgrade are not corrected.
- Anthropic on AWS Bedrock: synchronous `messages.create` (including `create(stream=True)`) and `messages.stream` calls on an `anthropic.AnthropicBedrock` client are now sent by the Anthropic SDK itself, so they behave exactly as they do without Revenium. Tools, tool choice, list-form system prompts, request metadata and thinking reach Bedrock, and a tool call comes back to your code. `create(stream=True)` returns the event stream instead of a single message that raised `TypeError` when iterated. The client's own access keys, profile, Bedrock API key and base URL (for example a VPC endpoint) are the ones used; before, the call ran under whatever AWS identity the machine had. A reply cut off at the token limit now reports `max_tokens` and is recorded as TOKEN_LIMIT instead of a normal finish. Short model names such as `claude-opus-4-7` still resolve to their Bedrock model IDs. Bedrock errors now reach you as the Anthropic SDK's own exceptions, with the SDK's own retries. These records now carry the message ID and model name Bedrock returns, as asynchronous Bedrock calls already did. A plain `anthropic.Anthropic` client pointed at a Bedrock URL is unchanged.
- Anthropic on AWS Bedrock: a non-streamed call through a client pointed at a Bedrock URL records the subscriber passed in the documented nested form (`usage_metadata={"subscriber": {"id": ..., "email": ...}}`). It was recorded with no subscriber, so per-person spend, budgets and subscriber reports missed those calls. The older flat `subscriber_id` / `subscriber_email` keys still work.
- Cost controls: a cost control set to warn only no longer stops your AI calls. Once a `WARN_ONLY` (or legacy `THROTTLE`) rule's cap was crossed, every wrapped OpenAI call raised `BudgetExceededError` and the LiteLLM gateway plugin answered 429, although Revenium and the Node and Go SDKs treat that rule as a notice. Such a call now goes through and the SDK logs one warning naming the rule, once per rule per budget window, not on every call. Only a rule whose action is `BLOCK` refuses calls; a rule with no action at all still counts as `BLOCK`.
- Cost controls: a per-person spending cap now stops a developer whose email reaches the SDK in mixed case or with stray spaces, such as `Jane.Doe@Acme.com`. Revenium keys each person by the email trimmed and lower-cased, and the SDK compared the address exactly as your code sent it, so that person's calls went through although the cap showed them as over. Subscriber ids are still matched exactly, as Revenium matches them. The same check also stops walking the whole list of people on every call: it now builds a lookup once per rules refresh, so its cost no longer grows with the size of your team (it took about 2.5 ms per cap per call at 30,000 people, on the LiteLLM gateway's event loop).
- Cost controls: a breached cap stops blocking when its budget window ends, even while Revenium's rules service cannot be reached and across restarts that reload the saved rules. Before, a cap breached late in a day kept refusing every call after midnight until a rules read succeeded again. The SDK now reads each rule's `windowEnd` on every call.
- Cost controls: when Revenium cannot read the per-person balances of a per-person cap, the cap no longer blocks everybody on the team because one person is over. A per-person rule that arrives with an empty balance list now blocks nobody until the balances come back; a team-wide cap is unchanged. A rules response with no content (HTTP 204) still clears the cached rules: Revenium sends that both for "this team has no cost controls" and for "the rules could not be read", and telling those apart needs a change on the Revenium side.
- Cost controls: a service for one team no longer starts up enforcing another team's cost limits when both share one `REVENIUM_CACHE_DIR`. The saved rules used one fixed file name, so a restarted process loaded whatever team had written last, along with that team's people's email addresses, and kept enforcing it if its own rules read failed. Saved rules are now named per team and environment (`revenium_enforcement_rules.<scope>.json`, where `<scope>` is a short hash of the enforcement base URL and `REVENIUM_TEAM_ID`), and a process loads only its own. Nothing is saved without `REVENIUM_TEAM_ID`. **Upgrade note:** the first start after upgrading finds no saved rules for its team and behaves as a cold start; with `REVENIUM_CB_FAIL_MODE=closed` calls are refused until the first successful rules read. The old `revenium_enforcement_rules.json` and `revenium_enforcement_org_unit_blocks.json` files are left in place and are no longer read; you can delete them once no older SDK version shares the folder.
- Perplexity: every call now records the cost Perplexity reports for it, including its flat per-request fee, so Perplexity spend shows in Revenium instead of $0. Perplexity returns its own charge with each response, and the Python SDK dropped it, so every Python Perplexity record was stored at $0 while the same call from the Go or Node SDK was priced; on a short `sonar` call about 80 percent of that charge is the per-request fee, which no token count can rebuild. Each record now carries Perplexity's reported total cost and its input and output token cost, for the native `perplexity` client and for the OpenAI client pointed at Perplexity, including `chat.completions.parse()`, streamed or not. A streamed call takes the cost from the last chunk that carries one. A response that reports no cost still leaves pricing to Revenium. Calls made before the upgrade are not repriced.
- Debug logging, and the error line for a usage record Revenium refuses, no longer print credentials, emails, prompts or replies. The 0.2.0 note that DEBUG logging no longer leaked them was incomplete: with `REVENIUM_LOG_LEVEL=DEBUG` (or `REVENIUM_DEBUG=true` for Anthropic) the SDK wrote each subscriber's credential value and email, and on several providers the model's reply, into your application logs on every call, through the metering client's own request line and the Ollama, LiteLLM (client and proxy), OpenAI, Google, Anthropic, Bedrock streaming and Perplexity integrations; Gemini system instructions, OpenAI Responses `instructions` and messages passed positionally printed too. With prompt capture on, every refused record also printed the system prompt, the user's messages, the reply and the subscriber's email at ERROR level, while the token counts were hidden. Every such line now redacts credentials, emails, secret-shaped values, prompt and reply fields in either spelling, free text and objects, and keeps token counts, ids, model names and attribution names; a refused record's error line now shows its status and token counts. What the SDK sends to Revenium is unchanged. A single-word prompt passed positionally (such as `ollama.generate("llama3", "hello")`) cannot be told apart from a model name and can still print.
- Outcomes, job calls and job-type economics calls go to the Revenium address you configured for usage. They used to default to a second, legacy address (`https://api.revenium.io`) and ignore `REVENIUM_METERING_BASE_URL`, so a setup that followed the README delivered usage records but could have every outcome refused. The outcome address is now, in order: `profitstream_base_url=`, `REVENIUM_PROFITSTREAM_BASE_URL`, your usage address (a trailing `/meter` is removed, a reverse-proxy path prefix is kept), then `https://api.revenium.ai`. A usage address set only in code with `initialize_metering(base_url=...)` is not followed; pass `profitstream_base_url=` in that case.
- Low-level outcome client: `emit_completion` forwards every field the completions API accepts. It used to drop 39 of them without a word, so a one-hour cache write was priced at the five-minute rate, batch and priority calls at the standard rate, a call marked `billingSkipped` was billed, and `ticketId`, `subscriptionId`, `squadRole`, the skill fields, `promptId`, `region`, `speed` and `temperature` never arrived. A key the API does not know is not sent, and is named in one warning per client (the key only, never its value).
- A job outcome that was stored but answered with a gateway error (502, 503 or 504) is no longer reported as `OutcomeAlreadyReportedError`. When the retry is refused as already reported, the SDK reads the job once; if the stored outcome is the one it sent and has not been amended, `report_outcome` succeeds and `JobContext.entity_version` holds the stored version, ready for an amendment. An identical outcome stored by another writer in that gap is reported as success too; `reported_by` and `metrics` are not part of the check. A real second report still raises. A timeout or connection error on the report itself is still not retried.
- Low-level outcome client: `emit_tool_event` sends one `Idempotency-Key` per call and reuses it on every retry, so a tool event retried after a gateway error is stored once instead of twice.
- Selective metering (`REVENIUM_SELECTIVE_METERING=true`): calls outside a `@revenium_meter` function no longer fail or send your Revenium metadata to the AI provider. An OpenAI or Anthropic call that passed `usage_metadata` raised `TypeError` and returned no answer, and LiteLLM and Perplexity calls sent that metadata, subscriber emails included, to the provider as a request field. The metadata is now removed before every provider call on every integration, including Vertex AI. Spending caps now also apply to OpenAI and LiteLLM client calls outside a metered function, as they do inside one; before, turning on selective metering silently switched those caps off. With `REVENIUM_CB_FAIL_MODE=closed`, such calls are refused until the first rules read completes, as metered calls already were. A `@revenium_meter` function that calls another one stays metered after the inner one returns; its later calls used to go unmetered, or fail on `usage_metadata`.
- Perplexity: a call on the native `perplexity` client that passes `usage_metadata=` directly, as the README's streaming example does, no longer fails with `TypeError`. The native client now accepts the metadata as `usage_metadata=` or inside `extra_body`, as the OpenAI client pointed at Perplexity already did, removes it before the request, and attributes the call, streamed or not. When both carry a field, `usage_metadata=` wins.
- LiteLLM client: spending caps are now checked by the LiteLLM client wrapper itself, with the caller's `usage_metadata` and any `@revenium_metadata` identity, before LiteLLM is called. A caller named only in LangChain's per-call settings (`config={"metadata": {"usage_metadata": ...}}`) is checked too. Following the README's earlier advice to get caps through the OpenAI middleware let a developer over a per-person or department cap keep calling, and a team cap reached your code as `litellm.InternalServerError`, which LiteLLM's retries and fallbacks treat as a provider outage. A blocked call now raises `BudgetExceededError` on every LiteLLM client completion and embedding entry point, sync and async, and LiteLLM's retries never send it to the provider. Requests the LiteLLM proxy serves are still enforced by the Revenium guardrail, not by the client wrapper.
- AI calls made inside a job whose id Revenium refuses on AI calls (a colon, space, slash or other character outside letters, digits, `.`, `_` and `-`, for example `order:42`) are no longer lost. Each such call was refused by Revenium and dropped with only an error line in your logs. Entering `JobContext` with such an id now raises `ValueError` naming the rule, before any call is made; an id refused this way can now only be used through `JobContext.attach()`, for a job created with `create_job`. An id from `usage_metadata`, `@track_job`, `REVENIUM_AGENTIC_JOB_ID` or proxy headers that breaks the rule is left off the call, which is still metered, and a warning is logged once per id.
- A `JobContext` block whose outcome report failed and was caught, and which then raised, now gets the automatic FAILED outcome the README promises; it used to end with no outcome. A failed report that itself escapes the block still sends no FAILED, and a report that found no such job does not rerun its retries on exit. If the failed report was in fact stored, the FAILED is refused as already reported and only logged.
- The README and docstrings now say that a job keeps one active fact per metric key: appending a key the job already has supersedes the earlier fact (deactivated, not deleted) and is refused without a `reason`, the same key twice in one request is refused, and on `amend_outcome` the amendment's reason is used. They used to say facts accumulate.
- Decorator tags reach every record, and nested decorators add to each other. A function decorated with `@revenium_metadata` inside another one replaced the outer tags for its own calls and then cleared them, so its calls lost the outer organization and every later call in the outer function had no decorator tags at all. Inner tags now sit on top of the outer ones, and the outer function keeps its tags after the inner returns. The `metadata` you give `@revenium_meter` now reaches the record, whether or not selective metering is on; before it was stored and never read. Gemini, Vertex AI, LiteLLM client and Bedrock `boto3` transport records now carry decorator tags too; before only the call's own `usage_metadata` reached them. A LangChain callback's metadata still beats the decorator, and the call's own `usage_metadata` beats both. Vertex AI image generation and image edit records now get the decorator tags too, and no longer pass your `usage_metadata` on to the Google call. The `operation_type` argument of `@revenium_meter` is deprecated; see Deprecated.
- A per-call transaction name, parent transaction id, retry number, environment, region, credential alias, trace type and trace name now win over the matching environment variables on every provider, as the README says. `REVENIUM_TRANSACTION_NAME` replaced a per-call `transaction_name` everywhere except OpenAI and Anthropic, and Ollama, Perplexity and fal ignored every per-call trace value, so records showed the deployment default instead of the operation you named. Gemini, Vertex AI, the LiteLLM client and the Bedrock `boto3` transport ignored a per-call retry number, and a per-call `retry_number` of 0 now beats a non-zero `REVENIUM_RETRY_NUMBER`, and that 0 is now recorded on Google, LiteLLM and Bedrock records instead of being dropped. Skill fields (`skill_name`, `skill_source` and the rest) now reach completion records from every provider, not only OpenAI. Bedrock streamed records now carry the trace fields at all. Environment variables still fill any field the call leaves unset, and `REVENIUM_TRANSACTION_NAME` still beats the `task_type` fallback.
- A `response_quality_score` of 0 is now recorded on OpenAI, Azure OpenAI, Gemini, Vertex AI and Perplexity calls. It was treated as missing and left off the record, so your lowest-scored responses had no score in Revenium. A call with no score still sends none.
- Ollama, Perplexity and LangChain callback records get a unique transaction id, so concurrent calls are no longer dropped. Ollama and Perplexity used the request time as the id and LangChain callback records used 8 random hex digits, so two calls in the same microsecond, or in separate processes, could share an id, and Revenium kept only the first. Ollama ids are now `ollama-` plus a full random UUID, a non-streamed Perplexity record uses Perplexity's own response id and a stream `perplexity-` (or `perplexity-sdk-` for the native client) plus a full random UUID, and LangChain callback ids are `langchain-` plus a full random UUID. If you match Perplexity transaction ids by their old `perplexity-<timestamp>` shape, update that match. Records already dropped are not recovered.
- OpenAI: streaming an answer while asking for the response headers works and is recorded once. `chat.completions.with_raw_response.create(stream=True)`, `with_streaming_response.create(stream=True)` and the Responses API equivalents, sync and async, raised `TypeError` or `AttributeError` after OpenAI had already charged for the call, and sent no usage record. LangChain's `ChatOpenAI` takes this route for every streamed call with `include_response_headers=True` or a LangSmith gateway key, so those streams broke as soon as Revenium was installed. You now get OpenAI's own response object back, untouched, and one record is sent once you have read the stream, whether through `parse()`, `read()`, `iter_bytes()` or `iter_lines()`; a response you never read sends none. The usage-only event Revenium asks OpenAI for is removed from the bytes you read unless you asked for usage yourself, so what you read is what you would read without Revenium. Reading the body with `iter_raw()` is not metered.
- Azure OpenAI: streamed chat calls are recorded. Azure opens every stream with a content-filter piece whose id and model are empty, and the SDK kept those empty values, so a sync stream sent no record and an async stream was recorded with no transaction id and model `unknown`. Streams now take the first id and model that are not empty.
- OpenAI: a streamed answer no longer keeps every piece in memory until it ends. Each open stream held about 2.5 KB per token (about 75 MB for a 30,000-token answer), so a server running many long streams at once could run out of memory. Memory now stays flat as the answer grows; the record is unchanged.
- Truncated answers are recorded with their real stop reason. Async OpenAI and Azure chat streams cut off by the token limit were recorded as a normal finish (`END`) and are now `TOKEN_LIMIT`, as sync streams already were; content-filter and tool-call stops on async streams are mapped too. OpenAI Responses calls, streamed or not, that end `incomplete` at the output limit are now `TOKEN_LIMIT`, `incomplete` from the content filter and `failed` are `ERROR`, instead of always `END`. A Claude answer that stops on one of your `stop_sequences` is now `END_SEQUENCE`, as Go, Node and the Bedrock transport already record it. Token counts and cost were already right; records made before the upgrade are not corrected.
- The credential alias now reaches Revenium. `REVENIUM_CREDENTIAL_ALIAS` and a per-call `credential_alias` were sent under a name Revenium does not read, so no record ever showed which provider key a call used, and nothing warned you. The alias is now sent as the subscriber's credential name, on every provider and on `emit_completion`. A call with no subscriber id or email is recorded under a credential named after the alias. A call that names a subscriber, by id or email, keeps that subscriber's own credential, and the SDK does not send the alias on it, so different subscribers are never linked to one shared credential. A credential name or value you set yourself on the subscriber (`subscriber.credential`, or `subscriber_credential_name` / `subscriber_credential`) still wins in what the SDK sends. If your team uses strict ingestion, register the alias as a credential first, or those records can be refused. A blank alias is ignored and surrounding spaces are removed. Records sent before the upgrade are not changed.
- LiteLLM gateway: environment, region, credential alias, transaction name, trace type, trace name, parent transaction id, retry number and skill settings now reach gateway records. Both `ReveniumGuardrail` and the deprecated `proxy_handler_instance` callback ignored them, so environment, region and skill reports left out all gateway traffic. Each record now takes these fields from a per-call header (`x-revenium-environment`, `x-revenium-region`, `x-revenium-credential-alias`, `x-revenium-transaction-name`, `x-revenium-trace-type`, `x-revenium-trace-name`, `x-revenium-parent-transaction-id`, `x-revenium-retry-number` and `x-revenium-skill-name`, `-skill-source`, `-skill-kind`, `-skill-plugin-name`, `-skill-marketplace-name`, `-skill-invocation-trigger`), else from the gateway host's own settings: `REVENIUM_ENVIRONMENT` (or `ENVIRONMENT`, or `DEPLOYMENT_ENV`), `REVENIUM_REGION` (or `AWS_REGION`, `AWS_DEFAULT_REGION`, `AZURE_REGION`, `GCP_REGION`, `GOOGLE_CLOUD_REGION`), `REVENIUM_CREDENTIAL_ALIAS`, `REVENIUM_TRANSACTION_NAME`, `REVENIUM_TRACE_TYPE`, `REVENIUM_TRACE_NAME`, `REVENIUM_PARENT_TRANSACTION_ID`, `REVENIUM_RETRY_NUMBER` and `REVENIUM_SKILL_*`. A gateway on a host that sets `ENVIRONMENT` or a cloud region variable now records it. Two differences from a direct call: the gateway does not fall back to the task type for the transaction name, and it sends a retry number only when the header or `REVENIUM_RETRY_NUMBER` sets one. The credential alias names the credential only on calls with no subscriber id or email and no virtual key alias; most virtual keys carry their owner's email, so those calls keep the owner's own credential. A caller's `x-revenium-credential-alias` wins over the host's alias, and a spending cap on a credential reads the same alias the record carries. Records sent before the upgrade are not changed.
- One-hour Claude cache writes are priced at the one-hour rate through LiteLLM (client mode, the `ReveniumGuardrail` gateway plugin and the deprecated proxy callback), the Bedrock transport (`REVENIUM_BEDROCK_TRANSPORT=1`: InvokeModel, its stream, Converse and ConverseStream) and the Bedrock fast path (a plain `anthropic.Anthropic` client pointed at a Bedrock endpoint). Anthropic and Bedrock charge a one-hour write at twice the input rate; these records carried only the total write, so Revenium priced all of it as a five-minute write at 1.25 times, about 37 percent low on that part of the bill. Each record now carries the five-minute and one-hour counts the provider reported, as the direct Anthropic integration already did, and that fast path's response `usage.cache_creation` now holds the split too. A Converse split is sent only when it accounts for the whole write. Calls whose response reports no split are unchanged. Separately, LiteLLM client-mode records for calls LiteLLM sends to Anthropic's API now count only the uncached prompt as input, as the gateway plugin already does: they counted the cache read and write a second time at the input rate, so a cached Claude call could be recorded at several times its real price. Claude through Bedrock or Vertex AI in LiteLLM is now netted the same way; see the LiteLLM Bedrock and Vertex AI entry below. Calls made before the upgrade are not corrected.
- LangChain: streamed Claude calls metered by the Revenium callback alone stop billing every cached prompt token twice. With `wrap(ChatAnthropic(...))` (or `ChatAnthropicBedrock`) and `stream` or `astream`, the record's input count included the cache read and write, which Revenium also priced on their own, so an agent call with a large cached prompt was stored at about ten times its real cost. The input count now holds only uncached tokens. Non-streamed LangChain Claude calls (`invoke`, `ainvoke`) now also carry the one-hour cache-write split, so one-hour writes are priced at the one-hour rate. A streamed call metered by the callback alone still prices a one-hour write at the five-minute rate, because Anthropic reports the split only at the start of the stream and langchain-anthropic does not pass it on; `import revenium_middleware.anthropic` before you create the model and those calls are recorded with the exact split. OpenAI and other LangChain records are unchanged. Calls made before the upgrade are not corrected.
- LiteLLM gateway: a blank or space-padded `REVENIUM_LITELLM_SHARED_CALL_ID` leaves the shared call id on, as the README promises for an unset value. A deployment template that passed the variable through empty (for example docker-compose `${REVENIUM_LITELLM_SHARED_CALL_ID}` with the host variable unset) silently turned it off, so every Claude Code call that also reports its own usage was stored twice. After upgrading, every `/v1/messages` client of such a gateway, not only Claude Code, gets the `request-id` and `x-revenium-transaction-id` response headers, and the stored transaction id becomes the minted UUID. `false` still turns it off, and so does any other value outside `true`, `1`, `yes`, `on`; the guardrail now logs at startup when it is off, with the value it read. Calls already stored twice are not merged.
- LiteLLM gateway: a blank organization or product header no longer stores the call under an empty value. An empty or whitespace `x-revenium-organization-name` (or the older `x-revenium-organization-id`) now falls back to the older header, the virtual key's team, then the key's `revenium_organization_name` metadata, exactly as when the header is absent, so the call stays in that team's cost reports. An empty `x-revenium-product-name` no longer hides a filled `x-revenium-product-id`. Filled headers are stored exactly as sent. Calls already stored are not corrected.
- LiteLLM: Claude calls through LiteLLM's Bedrock and Vertex AI routes no longer bill cached prompt tokens twice. LiteLLM counts the cache read and write inside its prompt count on these routes, and the SDK sent that count as input while Revenium also priced the same tokens at the cache rates, so a cache write cost about 1.8 times what Bedrock charged and a cache read about 10 times. Records for Claude on `bedrock` (Converse, invoke and mantle) and on `vertex_ai` now carry only the uncached input, with the cache counts unchanged, in client mode, the `ReveniumGuardrail` gateway plugin (including streamed `/v1/messages`, what Claude Code sends) and the deprecated proxy callback. The model is read from what LiteLLM reports it called, never from the alias in your request, so a gateway alias that names Claude in front of another model does not change that model's count. Gemini on Vertex AI, Nova and other non-Claude Bedrock models are unchanged. Some LiteLLM versions counted only the cache read inside the prompt count: the Anthropic-style routes (direct Anthropic, Vertex AI Claude and Bedrock invoke) on LiteLLM 1.66.0 to 1.77.2, and Bedrock Converse on 1.66.0 to 1.77.x. The SDK subtracts only what LiteLLM added on those versions. Known edge: a Bedrock application inference profile ARN that LiteLLM reports without a Claude model name is left as LiteLLM built it. Calls made before the upgrade are not corrected.
- LangChain: Claude calls through `ChatBedrockConverse` and `ChatAnthropicMantle` (langchain-aws) metered by the Revenium callback alone no longer bill cached prompt tokens twice. Both classes count the cache read and write inside `input_tokens`, and the record sent that count as input beside the cache counts. Streamed and non-streamed `ChatBedrockConverse` Claude calls, including a Claude application inference profile, and streamed `ChatAnthropicMantle` calls now carry only the uncached input; a Converse cache write with a TTL split is also sent as a cache write, where it was billed at the input rate with a cache-write count of 0. Nova and other non-Claude models on `ChatBedrockConverse`, and `ChatBedrock` (InvokeModel), are unchanged. langchain-aws below 1.4.6 already reported a net count and is left alone. Calls made before the upgrade are not corrected.

### Changed
- An attempt to send a usage record now gives up after 10 seconds without a response, not 60. Metering is sent off your request path, so the long wait bought nothing and held a background thread for up to three minutes per record when the endpoint stopped answering. A record that runs out of attempts still goes to the store-and-forward buffer and is sent later. Set `REVENIUM_METERING_TIMEOUT_SECONDS=60` for the old behaviour.
- `run_async_in_thread` queues the work and returns a handle instead of a started `threading.Thread`. The handle's `join(timeout)` and `is_alive()` follow the record's delivery as before; thread-only attributes such as `ident` and `daemon` are gone. At exit, within the `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS` budget described below, the SDK waits for queued records, builds the records that overflowed to the buffer, then flushes the buffer, stopping for usage records, or for tool events, at the first one their endpoint still cannot take. Records left at the end are dropped and one warning says how many, counting the records still queued, those not yet built, including any a running flush had set aside to build, and those the final flush did not send. Building the overflowed records at exit does not depend on starting a new thread, so they are still sent on Python 3.12.0 to 3.12.2, which refuse to start a thread from `atexit`, and in a process that has reached its thread limit. The one exception is work you passed to `run_async_in_thread` as a plain function rather than a coroutine: the budget cannot interrupt it, so when no thread can be started it is not run at exit and is counted in that warning.

### Fixed
- LiteLLM proxy, and any busy service: a slow or unreachable metering endpoint no longer piles up threads and memory. Every metered call started a thread of its own to send its usage record, and nothing limited how many could run at once. Each of those threads could wait minutes, through three attempts with a 60-second timeout and a queue for 100 shared connections, so when the endpoint hung or dropped connections the thread count grew with traffic: at 30 requests a second a LiteLLM proxy passed 2,000 threads within a minute and about 18,000 after ten, with memory growing by about 1 GiB. Usage records now go to a bounded queue that 32 background threads send from, so the thread count stays fixed whatever the traffic, and a call never waits on metering or starts a thread. 32 threads keep up with 30 records a second until a round trip to Revenium takes about a second; against an endpoint answering in 250 ms or 300 ms, 30 calls a second for five minutes were all delivered within 0.35 seconds. When the queue is full, new records go straight to the store-and-forward buffer and are sent with their original `Idempotency-Key` once the endpoint answers again, so they are counted once; one warning marks the start of each such episode and one, with a count, its end. When the endpoint stops answering, the threads no longer wait out three timed-out attempts per record: after three records in a row fail, new records go straight to the buffer unsent, one record every 5 seconds is still sent to check the endpoint, and the first success resumes sending and replays the buffer at once. Tool events from `@meter_tool` and `report_tool_call` keep being sent while AI records are held back, since `configure()` can send them to another endpoint, and the buffer replays them even while the AI records ahead of them are still failing.
- A Revenium outage of more than about a minute no longer loses usage records at 30 calls a second. The store-and-forward buffer held 1,000 records and evicted the oldest beyond that, so a ten-minute outage at 30 calls a second lost about 16,000 of 18,000 records, and it replayed one record per round trip, about 3 a second, so a backlog took most of an hour to drain. It now holds 20,000 records (`REVENIUM_BUFFER_MAX_SIZE`), eleven minutes at 30 a second or about 45 MB of typical records (lower it if you capture prompts, which makes records much larger), and replays 16 at a time; in a five-minute outage at 30 calls a second every record was held and then delivered once Revenium answered again. Records evicted from a full buffer are now counted in `get_metering_status().evicted_count`, not only in `get_buffer_stats()["total_evicted"]`, and logged with a count at most once per flush interval instead of a single warning for the whole outage.
- Ollama, LiteLLM, Perplexity and fal: a record's `response_time` and `request_duration` stay the call's own when metering is backed up. These integrations took the response time when the usage record was built, which with the queued delivery described above is when a background thread reaches the record, or, for a record that overflowed to the store-and-forward buffer, its next flush; a call the model answered in milliseconds would have been recorded as taking seconds or minutes whenever the queue was busy. Every integration now takes the response time when the provider answers, before the record is queued, and sends that value however long the record waits. Tool events from `@meter_tool` and `report_tool_call` likewise carry the time the tool finished, not the time the event was sent.
- The SDK no longer takes over SIGINT and SIGTERM. Importing `revenium_middleware` replaced both handlers with one that flushed metering and then ended the process with `os._exit(0)`, which skips everything the host still had to do on the way out: its `atexit` hooks, its cleanup, and its own graceful shutdown. The LiteLLM proxy imports its guardrails and callbacks after uvicorn has taken SIGTERM, so the SDK's handler replaced uvicorn's, the proxy's shutdown never ran, and a rolling restart lost LiteLLM's own spend-log rows. Signals now reach your application or server exactly as they would without the SDK, and uvicorn and the LiteLLM proxy shut down as they do on their own. The final flush of queued and buffered usage records runs from `atexit` when the interpreter exits, within one total budget of `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS` (5 seconds by default), instead of up to 5 seconds for each metering thread in turn; records still unsent at the deadline are logged once, with a count. A process that SIGTERM's default action ends skips `atexit`, so it now ends without that final flush and with SIGTERM's exit status (143) rather than 0; uvicorn and the LiteLLM proxy end this way once their own shutdown has finished, so events still buffered at that point are not replayed. For a script or worker with no SIGTERM handling of its own, set `REVENIUM_INSTALL_SIGNAL_HANDLERS=1` to flush first and then let SIGTERM end the process. With the flag set, a SIGTERM that arrives while the exit flush is already running lets that flush finish, within its budget, before the process ends. The SDK leaves SIGINT alone either way: Python's default Ctrl+C handling already exits through `atexit`.
- `REVENIUM_BUFFER_FLUSH_INTERVAL` set to `0`, a negative number or `nan` no longer makes the store-and-forward buffer replay in a tight loop: the background thread kept a CPU core busy and, with the endpoint down, sent it over a thousand requests a second. Set to `inf`, or to more seconds than Python can wait, it stopped background replay for the rest of the process. Such values now log a warning and use the 30-second default, as an unparseable value already did.
- OpenAI and Google: a usage record the SDK keeps in the store-and-forward buffer, because the endpoint was unreachable or the delivery queue was full, is no longer reported as a metering failure. The record was buffered and later sent, but the OpenAI integration also logged three `REVENIUM FAILURE` errors with a traceback for it, and the Google integration logged `REVENIUM FAILURE` and reported an extra error to `get_metering_status()` and `on_metering_error` callbacks, with `Error in metering thread` in the log. During an outage that meant a flood of errors for records that were not lost.
- SDK log lines are printed once when your application configures logging. Importing `revenium_middleware` before any logging was configured attached a handler of the SDK's own to the `revenium_middleware` logger, so an application that called `logging.basicConfig()` or added a root handler afterwards saw every SDK line twice, once in each format; importing `revenium_middleware.google` did the same when logging was configured first. ## [0.9.0] - 2026-09-24

### Added
- AI completions can now carry prompt, speed-mode and subagent attribution. `create_completion` (sync and async) accepts `prompt_id`, `prompt_length`, `query_source`, `speed` and `subagent_type`, and every provider integration that meters completions reads the same five from `usage_metadata` under their snake_case or camelCase names (`promptId`, `promptLength`, `querySource`, `speed`, `subagentType`), so a coding-assistant call can be grouped by the prompt that caused it, split into fast-mode and normal-mode spend, and attributed to the subagent that made it. Values are sent as given; the API owns the accepted formats. Unset fields are left off the request, so existing integrations send exactly what they did before. They apply to completions only: passing them on an image, video or audio call changes nothing. The LiteLLM proxy, which takes attribution from `x-revenium-*` headers, does not read them yet.
- You can now ask the enforcement API about **one** cost-limit rule instead of reading the whole team's. `revenium_middleware._core.fetch_enforcement_rule(rule_id)` sends the server's new `ruleId` filter on `GET /v2/api/ai/enforcement-rules/{teamId}` and returns that rule as the server compiled it, or `None` when the team has no such compiled rule (a disabled rule is never compiled) or the read could not be completed. It is an inspection call: it neither reads nor writes the cache the pre-call check evaluates, and it is never on the path of a metered call. The background poller and the stale-cache refresh keep reading the whole team, unchanged and byte-for-byte — narrowing them would drop the department-budget maps the server computes team-wide and attaches to that read, and department budgets would silently stop blocking anyone. That is the answer to "why was this caller blocked, and who else is this rule measuring?", which previously required reading the whole team's compiled payload and reassembling it by hand. `page`, `size`, `search` and `band` are passed to the server, which does the filtering, sorting, banding and paging; the band counts always describe the whole roster, so narrowing to one band cannot zero the other two. The roster is fetched on demand and never cached, so a stale roster cannot outlive the rule it describes, and nothing on the enforcement hot path reads it. It shares the rule fetch's retry, `Retry-After` budget, refresh cooldown and fail-open posture rather than issuing a bare request, so a throttled enforcement API sees one control-plane request, not two. Returns `None` when the rule has no compiled reading yet, the team has no such rule, or the read could not be completed.
- A Claude Code call that both Claude Code and your LiteLLM proxy report to Revenium can now be stored once instead of twice. `ReveniumGuardrail` mints one identifier per proxied Anthropic messages request, returns it to the client as the `request-id` and `x-revenium-transaction-id` response headers, and reports that same value as the call's transaction id. Claude Code copies `request-id` onto the usage record it reports itself, so the two records carry one identifier and Revenium's team-scoped duplicate check keeps one of them. On by default; set `REVENIUM_LITELLM_SHARED_CALL_ID=false` to opt out, and new calls go straight back to two records when you do; records already merged stay merged. Three preconditions: LiteLLM 1.93.0 or newer (the floor of the `litellm-proxy` extra, which is what installs the guardrail), a guardrail `mode` that includes `pre_call` (that is where the identifier is minted), and both sides reporting under keys of the same Revenium team. Opted out, every stored value is unchanged on every route. On a LiteLLM without the response-header hook, or under a `mode` that never runs the pre-call hook, the flag changes nothing and the guardrail logs one warning at startup naming the variable and the fix. Only the guardrail mints: a proxy still on the deprecated `MiddlewareHandler` callback alone keeps reporting two records, and a proxy running both without `default_on: true` sees its existing double count hidden rather than fixed, so delete the `litellm_settings.callbacks` entry. Other routes are untouched, so the provider's own `request-id` on the pass-through route is never overwritten, and a caller cannot decide their own transaction id by putting one in the request body. Point Claude Code at the proxy root (`ANTHROPIC_BASE_URL=<proxy>`) so it calls `<proxy>/v1/messages`: LiteLLM's Anthropic pass-through at `<proxy>/anthropic/v1/messages` is out of scope for the mint, and a proxy serving that route keeps counting the call twice with nothing in the log to say so.
- A LiteLLM proxy can now enforce a budget, not just report on one. `revenium_middleware.litellm.proxy.guardrail.ReveniumGuardrail` is a LiteLLM `CustomGuardrail` that blocks a call before it reaches the provider when a Revenium cost-limit rule is tripped, and meters it afterwards — successes, failures and streamed responses alike. Configure it under `litellm_settings.guardrails` with `mode: ["pre_call", "post_call"]` and `default_on: true`; see the README's LiteLLM "Proxy Mode". The pre-call decision is the SDK's own circuit breaker (`check_enforcement`, including the department/org-unit budget logic from 0.7/0.8), so a proxy enforces exactly what every other Revenium integration enforces, and a blocked caller receives HTTP 429 with a body naming the rule, its threshold, the caller's balance and when the window resets. Enforcement fails open — an unreachable or misbehaving enforcement path lets the call through — and metering is non-disruptive: the post-call hook runs in-band, so nothing it does can turn a successful LLM call into an error for the client. Metered rows carry the same `x-revenium-*` header attribution the callback records (with virtual-key metadata as the fallback), plus cache-token counts, `effort`, and `agenticJob*` tags, and are marked `middleware_source: "GUARDRAIL"`. Requires the `litellm-proxy` extra and Python 3.10+.
- Streamed proxied calls are metered with their assembled totals. LiteLLM hands the guardrail the complete response after a stream finishes, so a streamed call records real token counts and `is_streamed: true` rather than nothing. The vendor contract this depends on — that a guardrail defining no `async_post_call_streaming_iterator_hook` receives the assembled response through `async_post_call_success_hook` — is pinned by a test against litellm 1.100.1, so a LiteLLM upgrade that changes it fails in CI rather than silently in a customer's billing.

The runtime guards are unchanged: on a LiteLLM without the response-header hook, under a per-tag `mode`, or under a `mode` without `pre_call` nothing is minted, and the startup warning now fires there without the variable being set; set it to `false` on a metering-only proxy to silence it.

Detection is class-first from the client's MRO (so a custom gateway `base_url` cannot defeat it) with the `services.ai.azure.com` host as a fallback, and is evaluated after all Bedrock checks; `REVENIUM_BEDROCK_DISABLE` suppresses Bedrock detection only, leaving the Foundry label intact. The `litellm_settings.callbacks` string resolves to the same singleton as before.

### Fixed
- LiteLLM proxy: a call that reads from or writes to the prompt cache is priced once, so a gateway row costs what the provider charged. The metered `input_token_count` was LiteLLM's `prompt_tokens`, which counts the cache-read and cache-creation tokens inside it, and those same tokens were reported again in `cache_read_token_count` and `cache_creation_token_count`. Revenium prices the three separately and adds them up, so every cached token was billed at the input rate as well as at its own: one Claude Code call measured on dev recorded $0.0470 through the proxy against $0.0105 on Claude Code's own telemetry for the same call, and dashboards, budgets and alerts for that team ran on the inflated figure. For a call Anthropic served, `input_token_count` is now the tokens billed at the input rate only -- Anthropic's own `input_tokens` for the call, matching what the direct Anthropic integration reports -- with the cache counts unchanged in their own fields and the total still counting every bucket once. Every other provider's prompt count is reported exactly as before, because Revenium removes that overlap itself for the OpenAI-shaped cache pools (OpenAI, Groq, xAI, Azure, Gemini) and expects the gateway to report them gross; removing it twice would price their input at nothing. Anthropic is the one provider outside that set, which is why this is the only place its overlap can go. The upstream is read from LiteLLM's `custom_llm_provider` for the call (or the Anthropic messages route), and a call whose upstream cannot be identified keeps its prompt count untouched. Affects the `ReveniumGuardrail` post-call and streamed paths and both paths of the deprecated `MiddlewareHandler` callback. A call with no cache tokens is metered exactly as before, and rows already stored with the inflated count are not backfilled.
- LiteLLM proxy: a metered row's `request_time`, `response_time` and `completion_start_time` are the UTC instant, not the proxy machine's local wall clock. Every one of those values is published with a trailing `Z`, which means UTC, but the timestamps LiteLLM hands a logging callback carry no zone and read the machine's own clock, so a proxy outside UTC filed every row it metered from that path by its own offset. On a proxy in US Mountain time a call made at 8pm was stored as 2pm, moving evening calls onto the previous day in every hourly and daily chart and in date-range reports. That was hidden while Claude Code's own record carried the right time alongside it. With the shared call id on, which is the default, the proxy row is the one Revenium keeps, so it became the only recorded time. Affects the guardrail's streamed Anthropic route and both paths of the deprecated `MiddlewareHandler` callback. Rows metered from the non-streamed post-call path were already correct and are unchanged, as is every row on a proxy running in UTC.
- LiteLLM proxy: a **streamed** Claude Code call gets the same shared identifier as every other call on the Anthropic messages route, and the same header attribution. Streamed `/v1/messages` calls are metered from a different hook than the rest of the proxy, and that hook was added before the shared identifier and the route's header fix existed, so it filed its record under LiteLLM's own correlation id and read the request headers from the key this route does not fill. With the shared call id on, which is the default, the streamed record now carries the identifier the client was handed as `request-id`, which is what lets it merge with Claude Code's own record. Claude Code always streams, so this is the route the whole feature exists for. Your `x-revenium-*` headers are read from whichever key the route filled, matching the non-streamed record on the same route, and one call is still stored once no matter which hook reports it first. With `REVENIUM_LITELLM_SHARED_CALL_ID=false` the streamed record keeps LiteLLM's correlation id exactly as before.
- LiteLLM proxy: your `x-revenium-*` headers are read on the Anthropic messages route (`/v1/messages`), the route Claude Code and other Anthropic-shaped clients use. LiteLLM stores a request's headers under one of several keys depending on the route, and both the guardrail and the deprecated callback looked under one of them, which is not the one that route uses. The result was silent: calls were metered, but the trace id, subscriber, organization, product, subscription, task type, agent and `agenticJob*` tags you sent were all dropped, and per-subscriber budget enforcement on that route was applied to nobody. Headers are now read from whichever key the route filled, first non-empty wins, on metering and on pre-call enforcement alike. Headers set in the request body itself are read last and never override the ones LiteLLM captured, so one caller cannot attribute their spend to another.
- LiteLLM proxy: a Claude Code call made through your proxy carries its session identifier onto the metered record as the trace id, on both the guardrail and the deprecated callback. Claude Code stamps the same identifier on the usage records it reports directly, so the two views of one session can now be lined up. Note the effect on trace grouping: Revenium groups the trace list, session counts and parent-transaction joins by trace id, so a Claude Code session that previously appeared as one trace per call now appears as one trace per session. An `x-revenium-trace-id` header you set yourself always wins, and nothing about billing changes, because duplicate detection keys on the transaction id and never on the trace id.
- LiteLLM proxy: each failed attempt of a call is stored as its own record, on both the guardrail and the deprecated callback. A failure was recorded under the correlation id LiteLLM assigns the call, so two failures of one call collapsed into a single stored record, and a retried call could file its failed attempt under the same identity as the attempt you paid for. Every failure identity now ends in a marker and eight fresh characters unique to that attempt, which no successful call's identity can collide with. Correlation is unchanged: the identity still begins with the same id it did before.
- LiteLLM proxy: a failed proxied call is recorded as its own transaction. Both the guardrail and the deprecated callback metered every failure with the constant transaction id `"error-no-id"` (and the guardrail fell back to `"no-transaction-id"` on a success with no id). Revenium de-duplicates on (organization, transaction id) and passes non-UUID ids through unchanged, so for any one tenant every failed call after the first was acknowledged as a duplicate and never stored — the failure-rate signal disappeared exactly where it mattered. Each event now carries LiteLLM's own `litellm_call_id` (or the response id) when the request has one, and a fresh UUID when it does not.
- LiteLLM proxy: a failed embedding, rerank, image or transcription call is metered with its own operation type instead of being filed as `CHAT`. The success path has always read the operation off the response; the failure path hard-coded it, so the two disagreed about the same endpoint. It is now derived from the call type LiteLLM recorded, then the request endpoint, then the route the calling key was authorized against, and falls back to `CHAT` only when none of them resolves.
- LiteLLM proxy: a streamed call whose stream flag lives only on the response's own `_hidden_params` is metered with `is_streamed: true`. The payload builder re-derived the hidden params from request metadata alone rather than using the ones the hook had already resolved, so exactly the fallback branch that exists for that case was ignored.

### Deprecated
- `revenium_middleware.litellm.proxy.middleware.MiddlewareHandler` — the `litellm_settings.callbacks` entry `proxy_handler_instance` — is deprecated in favour of `ReveniumGuardrail`. It meters but never enforces a budget. It keeps working in this release and emits one `DeprecationWarning` and one log line when the proxy builds it, naming the guardrail and the README's "Migrating from the callback". Enabling both would meter every call twice; as a safety net for a proxy mid-migration, a guardrail configured to run on every request (`default_on: true` with `post_call` among its modes) claims metering ownership and the callback stops submitting rows, logging once to say so. That net deliberately does not apply to a guardrail without `default_on`, without `post_call`, or with a per-tag `Mode` that selects hooks per request — such a guardrail may not run on a given request, and suppressing the callback could drop metering entirely (a per-tag configuration logs, at info, that it is not claiming ownership). Delete the callbacks entry rather than relying on the net.

### Added
- An early warning before a department budget blocks you. The server publishes, with the enforcement rules, which people have crossed the warn tier of a per-person department (org-unit) cap without being blocked (`orgUnitBudgetWarnings`); the SDK now reads it and logs one warning naming the rule and — when the server publishes it — that person's own balance and the rule's threshold. Entries are forwarded exactly as supplied, so `provenance`, `recordedBy` and `source` keep their documented server-side defaults instead of being misattributed client-side; the SDK shape-checks each entry (a non-blank `key`, a `value`) before any request and leaves the economics rules to the platform, which requires the metric to be declared `PER_JOB` on the job type and range-checks `quality_rate` to 0..1. Facts are what AI Alerts evaluate `QUALITY_RATE` from, so an integration that could not emit them was invisible to those rules. Appending facts does not advance the job's `entityVersion`, so a handle keeps the version it recorded and a following `amend_outcome()` still locks against it. The append is retried only on `429` and never on an ambiguous gateway error, because a repeated append records a second fact rather than the same one.
- Agent version attribution on all four AI metering endpoints. Set `usage_metadata={"agent_version": "1.4.2"}` (or `agentVersion`) to record which release of your agent produced a call, and cost breaks down per agent version. Accepted on completions, audio, image and video together, forwarded by every provider integration, and capped at 64 characters to match the ingest contract. This is the agent's own version and is distinct from `agentic_job_version`, which versions the agentic job definition; the two never overwrite each other.
- Job type economics: `upsert_job_type_economics`, `get_job_type_economics`, `report_period_facts`, `create_baseline` and `list_baselines` (with the `JobTypeEconomics`, `PeriodFactEntry` and `Baseline` models) declare a job type's metrics and economics, append period facts and versioned baselines. Appends (facts, baselines) are retried only on `429`, never on an ambiguous gateway error, because a repeated append records a second fact.

### Changed
- `JobContext.amend_outcome()` accepts `expected_entity_version=` (the optimistic lock, defaulting to the version recorded by the handle's last report or amendment and omitted when none is known), and `reason` is now optional: an API-key caller may omit it and the platform records an automated correction reason derived from the source. `reason` remains the first positional argument, and a blank string is still rejected client-side. A version that is not a non-negative integer (`3.5`, `-1`, `True`) is rejected before the request rather than truncated.
- `AgenticOutcomeClient.create_job()` returns the created job resource parsed from the response — including its `entityVersion` — merged over the request body it sent, so a response that omits a field the caller supplied never drops it. An idempotent 409 re-run, a dry run and a bodiless response return the request body alone.
- Agentic outcomes documentation now standardizes on `REVENIUM_WRITE_API_KEY` as the primary write-scope key name. `REVENIUM_OUTCOME_API_KEY` remains documented as a deprecated fallback, and the documented resolution order is explicit `api_key=`, then `REVENIUM_WRITE_API_KEY`, then `REVENIUM_OUTCOME_API_KEY`, then `REVENIUM_METERING_API_KEY`.
- Enforcement rule refresh honours the server's `Retry-After` in full up to 20 seconds per call and then gives up for that cycle instead of refetching; the refresh cooldown is capped at 300 seconds so one absurd header cannot freeze rule refreshes.

## [0.4.0] - 2026-07-29

### Added
- Agentic job tracking with `JobContext`. Wrapping a unit of agent work in `with JobContext("loan-app-12345", type="loan_processing") as job:` meters every AI call made inside the block against that job — across all supported providers, with no per-call changes — and `job.report_outcome(...)` records the business result (`SUCCESS`, `FAILED`, or `CANCELLED`, plus an outcome type, value, and currency) so dashboards can show revenue impact next to AI spend. `async with` behaves identically. If an unhandled exception escapes the block before an outcome was reported, the job is automatically recorded as `FAILED` with the error details in metadata and the original exception is re-raised untouched. Nested contexts are treated as separate jobs, and exiting an inner context restores the outer job's fields.
- Outcome amendments and history. Business results change after the fact, so recorded outcomes can now be corrected instead of duplicated: `JobContext.attach("sales-lead-8842")` returns a lightweight handle to an existing job — usable from a different process than the one that ran it — whose `amend_outcome(reason=..., ...)` updates the stored outcome, while `get_outcome_history()` returns the full amendment trail in order. A dedicated exception family makes each failure mode explicit and catchable through the shared `OutcomeReportingError` base: `OutcomeAlreadyReportedError` (job already has an outcome — amend instead), `OutcomeNotReportedError` (nothing to amend yet), and `OutcomeAmendConflictError` (a concurrent amendment won the optimistic lock).
- Agentic job fields without a context manager, for code that cannot wrap its work in a block: the `@track_job()` decorator for LiteLLM (static values or extraction from function arguments), per-call `usage_metadata={"agentic_job_id": ...}`, or the process-wide `REVENIUM_AGENTIC_JOB_ID`, `REVENIUM_AGENTIC_JOB_NAME`, `REVENIUM_AGENTIC_JOB_TYPE`, and `REVENIUM_AGENTIC_JOB_VERSION` environment variables.
- Job outcome reporting for CrewAI. `ReveniumCrewWrapper` accepts `agentic_job_id`, `agentic_job_name`, `agentic_job_type`, and `agentic_job_version`, tying every LLM call the crew makes to a single job, and exposes `report_job_outcome()` and `amend_job_outcome()` for the business result.
- `ticket_id` trace field, threaded through metering for every provider integration (OpenAI, Anthropic including AWS Bedrock, Google Gemini and Vertex AI, Ollama, LiteLLM, Perplexity, and fal.ai). Set it per call via `usage_metadata={"ticket_id": "JIRA-123"}` or process-wide via `REVENIUM_TICKET_ID` to attribute AI cost to an individual ticket or issue.
- Tunable blocking behavior for outcome calls. Outcome reporting, amendment, and history retrieval are synchronous HTTP requests with retries; `retry_attempts`, `retry_initial_seconds`, and `retry_max_seconds` bound how long they may block, and are accepted by the `JobContext` constructor, `JobContext.attach()`, `get_outcome_history()`, and the CrewAI wrapper's outcome helpers.

### Changed
- The agentic outcomes API (reporting, amending, and reading job outcomes) requires a write-scope API key (`rev_sk_`). Metering keys (`rev_mk_`) meter completions and tool events only; the SDK now rejects them client-side with a clear error before any HTTP request is made, instead of surfacing a server-side authorization failure. Key resolution order is explicit `api_key=`, then `REVENIUM_OUTCOME_API_KEY`, then `REVENIUM_METERING_API_KEY`. The outcomes API base URL is configurable via `REVENIUM_PROFITSTREAM_BASE_URL`.
- Team resolution for outcome reporting follows explicit `team_id=`, then `REVENIUM_TEAM_ID`, then automatic resolution from the API key, raising `OutcomeReportingError` if none of those yields a team.

## [0.2.0] - 2026-07-09

### Added
- Store-and-forward buffering for metering events. Events that fail delivery with a transient error (connection failures, timeouts, rate limiting, or server errors) are no longer dropped: they are held in a bounded in-memory buffer and automatically replayed in the background once the backend is reachable again. Replayed events keep their original `Idempotency-Key`, so the backend safely deduplicates any overlap. The buffer is tunable via `REVENIUM_BUFFER_MAX_SIZE` (default 1000 events, oldest evicted first) and `REVENIUM_BUFFER_FLUSH_INTERVAL` (default 30 seconds); buffered events expire after 24 hours. A new `get_buffer_stats()` helper exposes buffer counters for observability, and a best-effort final drain runs at process exit.
- `initialize_metering(api_key=..., base_url=...)` for explicit programmatic (re)configuration of the metering client at runtime — useful for credential rotation or for configuring metering after import. Invalid keys raise immediately instead of failing silently.

### Changed
- Enforcement rule fetches now ride out transient failures (rate limits, server errors, connection errors) with exponential backoff capped at 8 seconds, honoring `Retry-After` headers. If retries are exhausted the SDK fails open and keeps the previously cached rules — an enforcement-refresh outage never blocks application traffic.
- Tool metering (`meter_tool` / `report_tool_call`) now dispatches events fire-and-forget on a background thread. Decorated functions and manual reporting return immediately instead of blocking on the metering network round-trip.

### Fixed
- Anthropic: raw streaming via `client.messages.create(stream=True)` is now metered. Previously only the `client.messages.stream()` context-manager path produced metering events.
- Streams abandoned before completion (early `break`, explicit `close()`, or garbage collection) now submit a metering event with the usage observed up to that point instead of silently dropping it. Applies to sync and async streams across providers.
- OpenAI streaming: when the middleware injects `stream_options={"include_usage": true}` to obtain token usage, the synthetic final usage chunk is no longer surfaced to callers that did not request it — the visible chunk sequence now matches the raw SDK exactly.
- Metering credentials set via environment variables after `revenium_middleware` is imported are now picked up on the next metering call; there is no longer an import-order requirement.
- Tool metering honors `configure()` overrides and environment variables at dispatch time and uses the correct metering API path.
- Anthropic on AWS Bedrock: the adapter now resolves the AWS region following boto3 conventions (client configuration, then `AWS_REGION`, then `AWS_DEFAULT_REGION`) instead of always defaulting to `us-east-1`.
- Anthropic on AWS Bedrock: genuine API errors from Bedrock calls now propagate to the caller instead of being masked by an internal fallback path.
- Streaming metering now reports `completion_start_time` as the arrival of the first stream event, improving time-to-first-token accuracy.
- DEBUG-level logging no longer leaks prompt or message content and credentials: sensitive fields (API keys, authorization headers, tokens) are redacted and message content is summarized across provider integrations.
