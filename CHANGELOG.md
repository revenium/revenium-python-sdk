# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.9.2] - 2026-10-07

### Added
- Ollama: calls through an explicit or async client are metered. Only the module-level `ollama.chat`, `ollama.generate` and `ollama.embed` were wrapped, and those talk to the default client on localhost, so a client pointed at your own server (`ollama.Client(host=...)`, the usual way to run Ollama), every `ollama.AsyncClient` call and the legacy `embeddings` call reached neither the dashboard nor billing, and nothing in the logs said so. `chat`, `generate`, `embed` and `embeddings` are now metered on `Client` and `AsyncClient`, streamed or not, and each call sends one record; the module-level functions still send one, not two. A stream you stop reading early is still metered once. `embeddings` responses carry no token counts, so those records are EMBED events with zero input tokens. With our LangChain callback attached, a `ChatOllama` call sends that one record too, not a second one from the callback.
- LiteLLM: `text_completion`, `atext_completion`, `completion_with_retries`, `acompletion_with_retries`, `embedding` and `aembedding` are metered. None of them passes through `litellm.completion`, so every one of those calls went unrecorded. The completion forms now record one event each with the response's model and token counts, streamed or not, and the embedding forms record one embedding event with the input token count. Passing `original_function=litellm.completion` to `completion_with_retries` still records the call once. `litellm.responses` and `litellm.aresponses` are still not metered, except on providers LiteLLM serves through `completion`, where the underlying completion is recorded.
- Anthropic: Claude calls made through the Anthropic client's beta interface are metered. `client.beta.messages.create(...)`, `client.beta.messages.create(..., stream=True)` and `client.beta.messages.stream()`, on `Anthropic` and `AsyncAnthropic`, sent no usage record at all and nothing in the logs said so, while the same calls through `client.messages` were metered. New Anthropic features ship on that interface first, and LangChain's `ChatAnthropic` uses it whenever `betas` is set. Each of those calls now sends one record with the response's model and its input, output and cache token counts, including through `with_raw_response` and `with_streaming_response`; beta-only usage fields such as server tool use are read past, not reported. `messages.parse()` and `beta.messages.parse()`, which post directly instead of going through `create`, are metered the same way, and so is every step of `beta.messages.tool_runner()`, streamed or not. With our LangChain callback attached, a `ChatAnthropic(betas=...)` call sends that one record, not a second one from the callback. On an `AnthropicBedrock` client these calls are recorded under AWS and are still served by the Anthropic SDK itself, not by the boto3 fast path `messages.create` takes. Message batches (`messages.batches` and `beta.messages.batches`) are still not metered: they bill when their results are retrieved, asynchronously, and need their own design. Calls made before the upgrade were never recorded and are not recovered.
- Metering delivery can be sized and its timeouts set. `REVENIUM_METERING_WORKERS` (default 32) and `REVENIUM_METERING_QUEUE_SIZE` (default 1000) size the background delivery described under Fixed. `REVENIUM_METERING_TIMEOUT_SECONDS` (default 10), `REVENIUM_METERING_CONNECT_TIMEOUT_SECONDS` (default 5) and `REVENIUM_METERING_MAX_RETRIES` (default 2) set how long one attempt to send a usage record may wait and how often it is retried. The two timeouts apply to tool events too, which waited 5 seconds whatever the setting, and a replay from the store-and-forward buffer waits at most `REVENIUM_METERING_TIMEOUT_SECONDS` instead of a fixed 10 seconds. `get_buffer_stats()` now also reports `total_overflowed`, the records that went to the store-and-forward buffer because the queue was full.

### Changed
- An attempt to send a usage record now gives up after 10 seconds without a response, not 60. Metering is sent off your request path, so the long wait bought nothing and held a background thread for up to three minutes per record when the endpoint stopped answering. A record that runs out of attempts still goes to the store-and-forward buffer and is sent later. Set `REVENIUM_METERING_TIMEOUT_SECONDS=60` for the old behaviour.
- `run_async_in_thread` queues the work and returns a handle instead of a started `threading.Thread`. The handle's `join(timeout)` and `is_alive()` follow the record's delivery as before; thread-only attributes such as `ident` and `daemon` are gone. At exit, within the `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS` budget described below, the SDK waits for queued records, builds the records that overflowed to the buffer, then flushes the buffer, stopping at the first record the endpoint still cannot take. Records left at the end are dropped and one warning says how many, counting the records still queued, those not yet built, including any a running flush had set aside to build, and those the final flush did not send. Building the overflowed records at exit does not depend on starting a new thread, so they are still sent on Python 3.12.0 to 3.12.2, which refuse to start a thread from `atexit`, and in a process that has reached its thread limit.

### Fixed
- LiteLLM proxy, and any busy service: a slow or unreachable metering endpoint no longer piles up threads and memory. Every metered call started a thread of its own to send its usage record, and nothing limited how many could run at once. Each of those threads could wait minutes, through three attempts with a 60-second timeout and a queue for 100 shared connections, so when the endpoint hung or dropped connections the thread count grew with traffic: at 30 requests a second a LiteLLM proxy passed 2,000 threads within a minute and about 18,000 after ten, with memory growing by about 1 GiB. Usage records now go to a bounded queue that 32 background threads send from, so the thread count stays fixed whatever the traffic, and a call never waits on metering or starts a thread. 32 threads keep up with 30 records a second until a round trip to Revenium takes about a second; against an endpoint answering in 250 ms or 300 ms, 30 calls a second for five minutes were all delivered within 0.35 seconds. When the queue is full, new records go straight to the store-and-forward buffer and are sent with their original `Idempotency-Key` once the endpoint answers again, so they are counted once; one warning marks the start of each such episode and one, with a count, its end. When the endpoint stops answering, the threads no longer wait out three timed-out attempts per record: after three records in a row fail, new records go straight to the buffer unsent, one record every 5 seconds is still sent to check the endpoint, and the first success resumes sending and replays the buffer at once.
- A Revenium outage of more than about a minute no longer loses usage records at 30 calls a second. The store-and-forward buffer held 1,000 records and evicted the oldest beyond that, so a ten-minute outage at 30 calls a second lost about 16,000 of 18,000 records, and it replayed one record per round trip, about 3 a second, so a backlog took most of an hour to drain. It now holds 20,000 records (`REVENIUM_BUFFER_MAX_SIZE`), eleven minutes at 30 a second or about 45 MB of typical records (lower it if you capture prompts, which makes records much larger), and replays 16 at a time; in a five-minute outage at 30 calls a second every record was held and then delivered once Revenium answered again. Records evicted from a full buffer are now counted in `get_metering_status().evicted_count`, not only in `get_buffer_stats()["total_evicted"]`, and logged with a count at most once per flush interval instead of a single warning for the whole outage.
- Ollama, LiteLLM, Perplexity and fal: a record's `response_time` and `request_duration` stay the call's own when metering is backed up. These integrations took the response time when the usage record was built, which with the queued delivery described above is when a background thread reaches the record, or, for a record that overflowed to the store-and-forward buffer, its next flush; a call the model answered in milliseconds would have been recorded as taking seconds or minutes whenever the queue was busy. Every integration now takes the response time when the provider answers, before the record is queued, and sends that value however long the record waits. Tool events from `@meter_tool` and `report_tool_call` likewise carry the time the tool finished, not the time the event was sent.
- The SDK no longer takes over SIGINT and SIGTERM. Importing `revenium_middleware` replaced both handlers with one that flushed metering and then ended the process with `os._exit(0)`, which skips everything the host still had to do on the way out: its `atexit` hooks, its cleanup, and its own graceful shutdown. The LiteLLM proxy imports its guardrails and callbacks after uvicorn has taken SIGTERM, so the SDK's handler replaced uvicorn's, the proxy's shutdown never ran, and a rolling restart lost LiteLLM's own spend-log rows. Signals now reach your application or server exactly as they would without the SDK, and uvicorn and the LiteLLM proxy shut down as they do on their own. The final flush of queued and buffered usage records runs from `atexit` when the interpreter exits, within one total budget of `REVENIUM_SHUTDOWN_TIMEOUT_SECONDS` (5 seconds by default), instead of up to 5 seconds for each metering thread in turn; records still unsent at the deadline are logged once, with a count. A process that SIGTERM's default action ends skips `atexit`, so it now ends without that final flush and with SIGTERM's exit status (143) rather than 0; uvicorn and the LiteLLM proxy end this way once their own shutdown has finished, so events still buffered at that point are not replayed. For a script or worker with no SIGTERM handling of its own, set `REVENIUM_INSTALL_SIGNAL_HANDLERS=1` to flush first and then let SIGTERM end the process. With the flag set, a SIGTERM that arrives while the exit flush is already running lets that flush finish, within its budget, before the process ends. The SDK leaves SIGINT alone either way: Python's default Ctrl+C handling already exits through `atexit`.
- `REVENIUM_BUFFER_FLUSH_INTERVAL` set to `0`, a negative number or `nan` no longer makes the store-and-forward buffer replay in a tight loop: the background thread kept a CPU core busy and, with the endpoint down, sent it over a thousand requests a second. Set to `inf`, or to more seconds than Python can wait, it stopped background replay for the rest of the process. Such values now log a warning and use the 30-second default, as an unparseable value already did.
- OpenAI and Google: a usage record the SDK keeps in the store-and-forward buffer, because the endpoint was unreachable or the delivery queue was full, is no longer reported as a metering failure. The record was buffered and later sent, but the OpenAI integration also logged three `REVENIUM FAILURE` errors with a traceback for it, and the Google integration logged `REVENIUM FAILURE` and reported an extra error to `get_metering_status()` and `on_metering_error` callbacks, with `Error in metering thread` in the log. During an outage that meant a flood of errors for records that were not lost.
- SDK log lines are printed once when your application configures logging. Importing `revenium_middleware` before any logging was configured attached a handler of the SDK's own to the `revenium_middleware` logger, so an application that called `logging.basicConfig()` or added a root handler afterwards saw every SDK line twice, once in each format; importing `revenium_middleware.google` did the same when logging was configured first. The SDK's handler now prints only while no root handler exists, so a script that never configures logging sees the same lines as before.
- LiteLLM proxy, and any async service, with budget checks on (`REVENIUM_CIRCUIT_BREAKER_ENABLED=true`): the proxy keeps serving while Revenium is unreachable, slow or rejecting your key. The budget check refreshed its rules inside the request whenever they were more than two minutes old, and LiteLLM runs that check on the one event loop that serves every request, so the whole proxy waited for the refresh: about a minute per request while the rules endpoint hung, about 8 seconds while it refused connections or returned 503, and one round trip per request while it returned 403. A failed refresh did not count as a refresh, so the next request started it all over again. At 30 requests a second a proxy served none of 5,400 requests in three minutes. The same check froze the caller's event loop in `AsyncOpenAI` calls. The check now judges each request against the rules already cached and never waits on the network; the background poller refreshes them, one refresh at a time per process, and a failed refresh is retried once per `REVENIUM_CB_POLL_INTERVAL_SECONDS` (60 seconds by default) however much traffic arrives, with a warning in the log. Right after startup, before the first fetch completes, there are no rules yet: calls go through at once, or are refused at once with `REVENIUM_CB_FAIL_MODE=closed`, rather than waiting for the fetch. What a known rule blocks is unchanged. Because the rules refresh no longer runs on a caller's thread, it now waits out a `Retry-After` of up to 60 seconds instead of 20; `fetch_enforcement_rule` and `fetch_enforcement_rule_roster` keep 20.
- Griptape: `ReveniumOllamaDriver` with `usage_metadata` no longer raises `TypeError: Client.chat() got an unexpected keyword argument 'usage_metadata'`. The driver calls an explicit `ollama.Client`, which was not wrapped, so the metadata reached Ollama's own method; its calls are now metered with that metadata (see the Ollama entry above).
- LiteLLM: asynchronous calls are metered. `litellm.acompletion` was never wrapped, so every async LiteLLM call, streamed or not, reached neither the dashboard nor billing, and nothing in the logs said so. That includes calls a LiteLLM `Router` makes on your behalf through `acompletion`. Each call now records one event with the model and token counts; a streamed call is recorded when the stream ends, is closed, or is abandoned. The stream you get back is still LiteLLM's own stream type, so code that checks for it keeps working. A LiteLLM proxy running `ReveniumGuardrail` with `default_on: true` and `post_call` among its modes still sends one record per request, the guardrail's: the proxy makes its calls through `acompletion` and `aembedding`, and the client integration leaves each of those to the guardrail instead of sending a second record. Streamed `/v1/completions` and `/v1/responses` requests, which the guardrail does not record, are still recorded by the client integration, and so is every call your own code in the proxy's process makes to LiteLLM directly.
- LiteLLM: a streamed completion that did not ask for usage is metered, and no longer logs `Error in metering thread`. Without `stream_options={"include_usage": True}`, `litellm.completion(stream=True)` produced no record, and our metering thread raised `AttributeError` on every call and logged it at ERROR, although your call succeeded. The SDK now asks LiteLLM for the usage chunk itself and meters from it, keeps any `stream_options` you pass, and keeps that extra chunk out of your stream unless you asked for usage yourself. This works for every provider: LiteLLM does not forward the option to providers that do not take it, such as Anthropic and Ollama, and still adds the usage chunk from the provider's own counts. If a stream still ends without usage, no record is sent and one warning is logged per process, not one error per call. A stream you stop reading early is still recorded, with zero token counts, as before.
- OpenAI: `client.chat.completions.stream()` and `client.responses.stream()` no longer raise with the middleware installed. On 0.9.1 and earlier, OpenAI's own streaming helpers raised as soon as the SDK was imported: the chat helper failed with `TypeError: 'Omit' object is not iterable` when the caller passed no `stream_options`, and with `AttributeError: ... has no attribute 'response'` when they did; the synchronous Responses helper failed with the same `AttributeError`. No configuration avoided it. The helpers now run to completion on both `OpenAI` and `AsyncOpenAI` and each call is metered once, with or without caller `stream_options`. A caller who did not ask for usage still does not see the extra usage chunk the SDK requests for metering, and one who asked still receives it.
- OpenAI: asynchronous Responses calls are metered. `AsyncOpenAI().responses.create(...)` was never wrapped, so every asynchronous Responses call, streamed or not, reached neither the dashboard nor billing, and nothing in the logs said so, while its synchronous twin was metered in the same process. Both forms now emit one event with the same model and the same input, output, total, cache-read and reasoning token counts as the synchronous call. `AsyncOpenAI().responses.stream()` is metered too, and `AsyncAzureOpenAI`, which uses the same client classes, is covered by the same change.
- OpenAI: streamed Responses calls are metered. `responses.create(..., stream=True)` produced no event at all, only the log warning `No usage data found in streaming Responses API response!`, because the SDK looked for the response id and usage at the top of each stream event and the Responses API delivers them nested under `event.response`. The SDK now reads the id, model and usage from there, including when the stream ends with `response.incomplete` or `response.failed`, so a streamed call records the same model and token counts, cache-read and reasoning included, as the non-streamed call for the same response. A stream abandoned before its final event is still metered once, with zero token counts. Calls made before the upgrade were never recorded and are not recovered.
- OpenAI: structured-output calls are metered. `client.chat.completions.parse(...)` and `client.responses.parse(...)`, the helpers that return a typed object from a Pydantic `response_format` or `text_format`, produced no usage record at all, sync or async, and nothing in the logs said so, because they send their request themselves instead of going through `create()`. Each call now sends one record with the model and the input, output, total, cache-read and reasoning token counts of the same `create()` call. LangChain's `with_structured_output`, which reaches OpenAI through `parse()`, is recorded once too, by the client and not a second time by our callback. A `parse()` that raises `LengthFinishReasonError` is recorded before the error reaches you, since OpenAI billed it; one that fails to validate against your model or is stopped by the content filter cannot be recorded, because OpenAI's client does not pass the response on with that error, and logs a WARNING saying the call was billed but not recorded. A `parse()` sent to Perplexity through the OpenAI client is budget-checked and recorded under PERPLEXITY. Calls made before the upgrade were never recorded and are not recovered.
- Anthropic: LangChain's `ChatAnthropic` works again with Anthropic metering turned on. LangChain sends every Claude call through the Anthropic client's `messages.with_raw_response.create`, and our integration read that call's result as if it were a finished message, so every `invoke` and `ainvoke` raised `AttributeError` after Anthropic had already served and charged for it, and every `stream` and `astream` returned normally but was never metered. The same applied to anyone calling `messages.with_raw_response.create` or `messages.with_streaming_response.create` directly, sync or async. Each of those calls now returns exactly the object it returns without the SDK (the same response type, request id, status and cached `parse()` result, and a `with_streaming_response` body left unread for you to read, stream or abandon) and sends one usage record with the response's model and token counts. `with_streaming_response` calls and streamed raw-response calls are metered from the body as you read it, whether through `parse()` or the raw bytes, so a body you never read is not metered, as with `messages.create(stream=True)`. With our LangChain callback also attached, a `ChatAnthropic` call sends that one record too, not a second one from the callback (see the LangChain entry below).
- LangChain: each model call is metered once, under its own provider. Importing `revenium_middleware.openai.langchain` also turns on OpenAI client metering, so with our callback attached every `ChatOpenAI` call sent two usage records with different ids, one from the callback and one from the client, and reported cost and tokens were double what was spent. That held for `invoke`, `ainvoke`, `stream`, `astream`, `wrap()` and callbacks passed in `config`; only streams with `stream_usage=False`, or with a custom client or base URL, sent one. The callback now sends nothing when our OpenAI or Anthropic client metering records the call, and the record kept is the client's, with the provider's own response id, the dated model name and `is_streamed` on streams. That record keeps the `usage_metadata` you gave the callback (through `wrap(...)`, `attach_to(...)` or `ReveniumCallbackHandler(...)`), so subscriber, organization, product, trace, task and the other attribution fields still reach per-user and per-organization reporting; without this, the callback standing down would have dropped them from every one of those calls. That holds for `invoke`, `ainvoke`, `stream`, `astream` and `with_structured_output` on `ChatOpenAI`, for `ChatAnthropic` with or without `betas`, and for `ChatOllama` calls the Ollama client meters. `usage_metadata` passed on the call itself, such as `llm.bind(usage_metadata=...)`, still wins field by field over the callback's, and budget enforcement sees the merged fields. For async calls the callback now runs inline on LangChain's event loop instead of on a worker thread, which is what lets its metadata reach the client's record. A call only the callback sees, such as `ChatAnthropic` without `revenium_middleware.anthropic` imported, is recorded under its own provider (ANTHROPIC for `ChatAnthropic`) instead of OPENAI, with the dated model the provider reported and `is_streamed` true on `stream` and `astream`. The provider is read from the LangChain model for OpenAI, Azure OpenAI, Anthropic and Ollama models; models from any other provider still carry the OPENAI label. Records already sent twice are not merged.
- Google GenAI: calls made through the async client are metered. `client.aio.models.generate_content`, `generate_content_stream`, `embed_content` and `generate_images`, and chat messages sent with `client.aio.chats.create(...).send_message` or `send_message_stream`, were never wrapped, so a service that moved its Gemini calls to async stopped reporting usage with no error or warning, while the same calls through the sync client were metered. Each async call now sends one record with the same model and token counts as its sync twin: one per generation, one per streamed generation (also when you stop reading the stream early, close it, or it fails partway), one embedding record without token counts (the Gemini API does not return any for embeddings), one image record per `generate_images` call, and one per chat message. `usage_metadata` is accepted on the async calls as on the sync ones, and with selective metering on it is now dropped before the call on both clients instead of reaching google-genai, which rejected it. Calls made before the upgrade were never recorded and are not recovered.
- fal: runs through a client you construct yourself, and jobs run through fal's queue, are metered. Only the module-level functions (`fal_client.run`, `subscribe`, `stream` and their async variants) were wrapped, so `fal_client.SyncClient(key=...)` and `AsyncClient(key=...)` calls, and the `submit`, `status`, `result` flow that long image and video jobs normally use, reached neither the dashboard nor billing, with nothing in the logs. Each of those now sends one record with the same model and image, video or audio fields as the module-level call. A queued job is metered once, when its result is fetched, whether through `subscribe`, the handle's `get()` or `result(application, request_id)`: `submit` and `status` send nothing, fetching the same result again sends nothing more, and a job whose result you never fetch is not metered. `subscribe` and the module-level functions still send exactly one record each. `usage_metadata` is accepted on `submit` as well as `run`, `subscribe` and `stream`, and a `subscribe` with `client_timeout` keeps the caller's metadata and `@revenium_meter` scope. `fal_client.stream_async` no longer raises with the middleware installed: it failed with `TypeError: 'async for' requires an object with __aiter__ method, got coroutine` on 0.9.1 and earlier, and is now metered once when the stream has been read to the end, as `stream` is. Runs made before the upgrade were never recorded and are not recovered.
- Perplexity: the official Perplexity client is metered. On 0.9.1 and earlier, `Perplexity().chat.completions.create(...)` produced no usage record at all, because our integration wrapped a class name `perplexityai` does not ship (its chat resource has been `CompletionsResource` since chat arrived); the failure was logged only at debug level, and `is_patched` still reported the integration as installed, so nothing pointed at the missing usage. Sync and `AsyncPerplexity` calls, streamed or not, now each send one record with the response's input and output token counts. With only the `perplexity-native` extra installed (no `openai` package), the Perplexity integration used to fail to load altogether and now loads and meters the native client. Perplexity reached through `AsyncOpenAI(base_url="https://api.perplexity.ai")` is metered too, once, whether or not the OpenAI integration is also imported; a plain `AsyncOpenAI` call with both imported is still metered once, as OPENAI. A Perplexity stream you stop reading partway and never close, on either client, still sends one record, with the usage it had received, once your code lets go of it, as `OpenAI(base_url="https://api.perplexity.ai")` streams did on 0.9.1; a stream read to the end or closed still sends exactly one. A Perplexity wrap that cannot be applied is now logged as a warning naming the target, and `is_patched` reports it as not installed. Calls made before the upgrade were never recorded and are not recovered.
- Vertex AI: asynchronous calls and chat-session messages are metered. Only `GenerativeModel.generate_content` and `TextEmbeddingModel.get_embeddings` were wrapped, so `generate_content_async` (streamed or not), `get_embeddings_async`, and every message sent through a chat session (`model.start_chat().send_message(...)` and `send_message_async(...)`, streamed or not) reached neither the dashboard nor billing, and nothing in the logs said so. A chat session sends through a private model method, so even a synchronous chat skipped the wrapped `generate_content`. Each of these calls now records one event with the same model and token counts as the equivalent `generate_content` or `get_embeddings` call, each message of a conversation is its own record, and no message is counted twice. The `vertexai.preview.generative_models` classes are covered too. With the preview automatic function-calling responder, a message that makes several model calls is recorded once, with the last call's token counts. Calls made before the upgrade were never recorded and are not recovered.

## [0.9.1] - 2026-09-28

### Added
- LiteLLM proxy: a call made through a virtual key several people share can now say who made it. Send `x-revenium-subscriber-email` (or the same key in the request's `metadata`) and the call is metered, and checked against per-person and department budgets, as that person instead of the key's owner. Before, every call on a shared key counted against its owner: cost reports and budgets followed one person, and a developer blocked by their department's cap kept getting through on the owner's balance. A call that names someone other than the key owner by email only is not given the key's `revenium_user_id`, so per-person limits check that person's balance, not the owner's; an owner sending their own address keeps the key's id. Without the header the key owner's email and id are used, exactly as before. The value is taken as the caller sends it, the same trust `x-revenium-subscriber-id` already carries. Applies to `ReveniumGuardrail` and the deprecated `MiddlewareHandler` callback. On a team with strict ingestion enabled, the email must belong to a registered user: a mistyped or unregistered address gets the call's metering row rejected, not filed under the key owner.

### Changed
- LiteLLM proxy: `x-revenium-subscriber-id` is read from the header the proxy received before a copy of the same key in the request's `metadata`, on both the guardrail and the deprecated callback. The two only differ when a client sends both with different values; the header now wins. A blank header or metadata value is ignored rather than recorded.

### Fixed
- Department budgets block and warn again. On 2026-09-27 the Revenium platform renamed the department fields of the enforcement payload (`orgUnitBudgetBlocks`, `orgUnitBudgetBlockBalances` and `orgUnitBudgetWarnings` became `departmentBudgetBlocks`, `departmentBudgetBlockBalances` and `departmentBudgetWarnings`; a department rule's `groupBy` became `DEPARTMENT` and its `orgUnitId` became `departmentId`). 0.9.0 and earlier only read the old names and enforcement fails open on a missing field, so a developer over their department cap was let through with no error and no warning. The SDK now reads the department names. It still reads the org-unit names when a platform serves only those, and prefers the department names when both are present; that compatibility will be dropped in a later release. No configuration change is needed.

## [0.9.0] - 2026-09-24

### Added
- AI completions can now carry prompt, speed-mode and subagent attribution. `create_completion` (sync and async) accepts `prompt_id`, `prompt_length`, `query_source`, `speed` and `subagent_type`, and every provider integration that meters completions reads the same five from `usage_metadata` under their snake_case or camelCase names (`promptId`, `promptLength`, `querySource`, `speed`, `subagentType`), so a coding-assistant call can be grouped by the prompt that caused it, split into fast-mode and normal-mode spend, and attributed to the subagent that made it. Values are sent as given; the API owns the accepted formats. Unset fields are left off the request, so existing integrations send exactly what they did before. They apply to completions only: passing them on an image, video or audio call changes nothing. The LiteLLM proxy, which takes attribution from `x-revenium-*` headers, does not read them yet.
- You can now ask the enforcement API about **one** cost-limit rule instead of reading the whole team's. `revenium_middleware._core.fetch_enforcement_rule(rule_id)` sends the server's new `ruleId` filter on `GET /v2/api/ai/enforcement-rules/{teamId}` and returns that rule as the server compiled it, or `None` when the team has no such compiled rule (a disabled rule is never compiled) or the read could not be completed. It is an inspection call: it neither reads nor writes the cache the pre-call check evaluates, and it is never on the path of a metered call. The background poller and the stale-cache refresh keep reading the whole team, unchanged and byte-for-byte — narrowing them would drop the department-budget maps the server computes team-wide and attaches to that read, and department budgets would silently stop blocking anyone. An empty `rule_id` raises `ValueError` rather than quietly reading the whole team.
- You can now see **who** a cost-limit rule actually covers. `revenium_middleware._core.fetch_enforcement_rule_roster(rule_id)` reads `GET /v2/api/ai/enforcement-rules/{teamId}/roster` and returns the people (or departments) the rule is measuring — each with their spend, their cap, their band and their last enforcement event — beside the whole roster's blocked, warned and under counts. That is the answer to "why was this caller blocked, and who else is this rule measuring?", which previously required reading the whole team's compiled payload and reassembling it by hand. `page`, `size`, `search` and `band` are passed to the server, which does the filtering, sorting, banding and paging; the band counts always describe the whole roster, so narrowing to one band cannot zero the other two. The roster is fetched on demand and never cached, so a stale roster cannot outlive the rule it describes, and nothing on the enforcement hot path reads it. It shares the rule fetch's retry, `Retry-After` budget, refresh cooldown and fail-open posture rather than issuing a bare request, so a throttled enforcement API sees one control-plane request, not two. Returns `None` when the rule has no compiled reading yet, the team has no such rule, or the read could not be completed.
- A Claude Code call that both Claude Code and your LiteLLM proxy report to Revenium can now be stored once instead of twice. `ReveniumGuardrail` mints one identifier per proxied Anthropic messages request, returns it to the client as the `request-id` and `x-revenium-transaction-id` response headers, and reports that same value as the call's transaction id. Claude Code copies `request-id` onto the usage record it reports itself, so the two records carry one identifier and Revenium's team-scoped duplicate check keeps one of them. On by default; set `REVENIUM_LITELLM_SHARED_CALL_ID=false` to opt out, and new calls go straight back to two records when you do; records already merged stay merged. Three preconditions: LiteLLM 1.93.0 or newer (the floor of the `litellm-proxy` extra, which is what installs the guardrail), a guardrail `mode` that includes `pre_call` (that is where the identifier is minted), and both sides reporting under keys of the same Revenium team. Opted out, every stored value is unchanged on every route. On a LiteLLM without the response-header hook, or under a `mode` that never runs the pre-call hook, the flag changes nothing and the guardrail logs one warning at startup naming the variable and the fix. Only the guardrail mints: a proxy still on the deprecated `MiddlewareHandler` callback alone keeps reporting two records, and a proxy running both without `default_on: true` sees its existing double count hidden rather than fixed, so delete the `litellm_settings.callbacks` entry. Other routes are untouched, so the provider's own `request-id` on the pass-through route is never overwritten, and a caller cannot decide their own transaction id by putting one in the request body. Point Claude Code at the proxy root (`ANTHROPIC_BASE_URL=<proxy>`) so it calls `<proxy>/v1/messages`: LiteLLM's Anthropic pass-through at `<proxy>/anthropic/v1/messages` is out of scope for the mint, and a proxy serving that route keeps counting the call twice with nothing in the log to say so.
- A LiteLLM proxy can now enforce a budget, not just report on one. `revenium_middleware.litellm.proxy.guardrail.ReveniumGuardrail` is a LiteLLM `CustomGuardrail` that blocks a call before it reaches the provider when a Revenium cost-limit rule is tripped, and meters it afterwards — successes, failures and streamed responses alike. Configure it under `litellm_settings.guardrails` with `mode: ["pre_call", "post_call"]` and `default_on: true`; see the README's LiteLLM "Proxy Mode". The pre-call decision is the SDK's own circuit breaker (`check_enforcement`, including the department/org-unit budget logic from 0.7/0.8), so a proxy enforces exactly what every other Revenium integration enforces, and a blocked caller receives HTTP 429 with a body naming the rule, its threshold, the caller's balance and when the window resets. Enforcement fails open — an unreachable or misbehaving enforcement path lets the call through — and metering is non-disruptive: the post-call hook runs in-band, so nothing it does can turn a successful LLM call into an error for the client. Metered rows carry the same `x-revenium-*` header attribution the callback records (with virtual-key metadata as the fallback), plus cache-token counts, `effort`, and `agenticJob*` tags, and are marked `middleware_source: "GUARDRAIL"`. Requires the `litellm-proxy` extra and Python 3.10+.
- Streamed proxied calls are metered with their assembled totals. LiteLLM hands the guardrail the complete response after a stream finishes, so a streamed call records real token counts and `is_streamed: true` rather than nothing. The vendor contract this depends on — that a guardrail defining no `async_post_call_streaming_iterator_hook` receives the assembled response through `async_post_call_success_hook` — is pinned by a test against litellm 1.100.1, so a LiteLLM upgrade that changes it fails in CI rather than silently in a customer's billing.

### Changed
- LiteLLM proxy: the shared call id is on by default. A fresh install of `ReveniumGuardrail` with no `REVENIUM_LITELLM_SHARED_CALL_ID` set now mints the identifier, returns it as `request-id`, and reports it as the call's transaction id, so a Claude Code call that both Claude Code and the proxy report is stored once without the customer having to find the variable first. It shipped off so the first release could be observed on dev; that observation showed every call stored twice with the default and once with the id on. Set `REVENIUM_LITELLM_SHARED_CALL_ID=false` to keep LiteLLM's own response id as the transaction id and add no `request-id` header, exactly as before. The runtime guards are unchanged: on a LiteLLM without the response-header hook, under a per-tag `mode`, or under a `mode` without `pre_call` nothing is minted, and the startup warning now fires there without the variable being set; set it to `false` on a metering-only proxy to silence it.
- Claude served through Microsoft Foundry is attributed to its own `Foundry` provider bucket instead of being counted as direct Anthropic traffic. Foundry calls go through the same patched `messages` endpoints as the direct API and fell through provider detection, so Foundry spend landed in the direct-Anthropic bucket where an administrator reconciling against a Microsoft invoice could not find it. Detection is class-first from the client's MRO (so a custom gateway `base_url` cannot defeat it) with the `services.ai.azure.com` host as a fallback, and is evaluated after all Bedrock checks; `REVENIUM_BEDROCK_DISABLE` suppresses Bedrock detection only, leaving the Foundry label intact. Everything else on the payload is unchanged.
- The `litellm-proxy` extra requires `litellm[proxy]>=1.93.0`, up from `>=1.40.0`, for the `CustomGuardrail` lifecycle hooks and the deferred post-stream guardrail dispatch. The `litellm` (client) extra and `requires-python >= 3.8` are unchanged, and a client-only install pulls neither `litellm[proxy]` nor FastAPI. The guardrail module carries an import guard that raises a clear `ImportError` on Python < 3.10, which `litellm[proxy]` does not support; `revenium_middleware.litellm.proxy.ReveniumGuardrail` is `None` there and the rest of the LiteLLM integration is unaffected.
- `revenium_middleware.litellm.proxy.middleware.proxy_handler_instance` is built on first access rather than at import, so importing the SDK's LiteLLM subpackage no longer constructs the deprecated handler (and no longer emits its `DeprecationWarning`) at a caller who only uses the guardrail. The `litellm_settings.callbacks` string resolves to the same singleton as before.

### Fixed
- LiteLLM proxy: a call that reads from or writes to the prompt cache is priced once, so a gateway row costs what the provider charged. The metered `input_token_count` was LiteLLM's `prompt_tokens`, which counts the cache-read and cache-creation tokens inside it, and those same tokens were reported again in `cache_read_token_count` and `cache_creation_token_count`. Revenium prices the three separately and adds them up, so every cached token was billed at the input rate as well as at its own: one Claude Code call measured on dev recorded $0.0470 through the proxy against $0.0105 on Claude Code's own telemetry for the same call, and dashboards, budgets and alerts for that team ran on the inflated figure. For a call Anthropic served, `input_token_count` is now the tokens billed at the input rate only -- Anthropic's own `input_tokens` for the call, matching what the direct Anthropic integration reports -- with the cache counts unchanged in their own fields and the total still counting every bucket once. Every other provider's prompt count is reported exactly as before, because Revenium removes that overlap itself for the OpenAI-shaped cache pools (OpenAI, Groq, xAI, Azure, Gemini) and expects the gateway to report them gross; removing it twice would price their input at nothing. Anthropic is the one provider outside that set, which is why this is the only place its overlap can go. The upstream is read from LiteLLM's `custom_llm_provider` for the call (or the Anthropic messages route), and a call whose upstream cannot be identified keeps its prompt count untouched. Affects the `ReveniumGuardrail` post-call and streamed paths and both paths of the deprecated `MiddlewareHandler` callback. A call with no cache tokens is metered exactly as before, and rows already stored with the inflated count are not backfilled.
- LiteLLM proxy: a metered row's `request_time`, `response_time` and `completion_start_time` are the UTC instant, not the proxy machine's local wall clock. Every one of those values is published with a trailing `Z`, which means UTC, but the timestamps LiteLLM hands a logging callback carry no zone and read the machine's own clock, so a proxy outside UTC filed every row it metered from that path by its own offset. On a proxy in US Mountain time a call made at 8pm was stored as 2pm, moving evening calls onto the previous day in every hourly and daily chart and in date-range reports. That was hidden while Claude Code's own record carried the right time alongside it. With the shared call id on, which is the default, the proxy row is the one Revenium keeps, so it became the only recorded time. Affects the guardrail's streamed Anthropic route and both paths of the deprecated `MiddlewareHandler` callback. Rows metered from the non-streamed post-call path were already correct and are unchanged, as is every row on a proxy running in UTC.
- LiteLLM proxy: a **streamed** Claude Code call gets the same shared identifier as every other call on the Anthropic messages route, and the same header attribution. Streamed `/v1/messages` calls are metered from a different hook than the rest of the proxy, and that hook was added before the shared identifier and the route's header fix existed, so it filed its record under LiteLLM's own correlation id and read the request headers from the key this route does not fill. With the shared call id on, which is the default, the streamed record now carries the identifier the client was handed as `request-id`, which is what lets it merge with Claude Code's own record. Claude Code always streams, so this is the route the whole feature exists for. Your `x-revenium-*` headers are read from whichever key the route filled, matching the non-streamed record on the same route, and one call is still stored once no matter which hook reports it first. With `REVENIUM_LITELLM_SHARED_CALL_ID=false` the streamed record keeps LiteLLM's correlation id exactly as before.
- LiteLLM proxy: your `x-revenium-*` headers are read on the Anthropic messages route (`/v1/messages`), the route Claude Code and other Anthropic-shaped clients use. LiteLLM stores a request's headers under one of several keys depending on the route, and both the guardrail and the deprecated callback looked under one of them, which is not the one that route uses. The result was silent: calls were metered, but the trace id, subscriber, organization, product, subscription, task type, agent and `agenticJob*` tags you sent were all dropped, and per-subscriber budget enforcement on that route was applied to nobody. Headers are now read from whichever key the route filled, first non-empty wins, on metering and on pre-call enforcement alike. Headers set in the request body itself are read last and never override the ones LiteLLM captured, so one caller cannot attribute their spend to another.
- LiteLLM proxy: a Claude Code call made through your proxy carries its session identifier onto the metered record as the trace id, on both the guardrail and the deprecated callback. Claude Code stamps the same identifier on the usage records it reports directly, so the two views of one session can now be lined up. Note the effect on trace grouping: Revenium groups the trace list, session counts and parent-transaction joins by trace id, so a Claude Code session that previously appeared as one trace per call now appears as one trace per session. An `x-revenium-trace-id` header you set yourself always wins, and nothing about billing changes, because duplicate detection keys on the transaction id and never on the trace id.
- LiteLLM proxy: each failed attempt of a call is stored as its own record, on both the guardrail and the deprecated callback. A failure was recorded under the correlation id LiteLLM assigns the call, so two failures of one call collapsed into a single stored record, and a retried call could file its failed attempt under the same identity as the attempt you paid for. Every failure identity now ends in a marker and eight fresh characters unique to that attempt, which no successful call's identity can collide with. Correlation is unchanged: the identity still begins with the same id it did before.
- LiteLLM proxy: a failed proxied call is recorded as its own transaction. Both the guardrail and the deprecated callback metered every failure with the constant transaction id `"error-no-id"` (and the guardrail fell back to `"no-transaction-id"` on a success with no id). Revenium de-duplicates on (organization, transaction id) and passes non-UUID ids through unchanged, so for any one tenant every failed call after the first was acknowledged as a duplicate and never stored — the failure-rate signal disappeared exactly where it mattered. Each event now carries LiteLLM's own `litellm_call_id` (or the response id) when the request has one, and a fresh UUID when it does not.
- LiteLLM proxy: a failed embedding, rerank, image or transcription call is metered with its own operation type instead of being filed as `CHAT`. The success path has always read the operation off the response; the failure path hard-coded it, so the two disagreed about the same endpoint. It is now derived from the call type LiteLLM recorded, then the request endpoint, then the route the calling key was authorized against, and falls back to `CHAT` only when none of them resolves.
- LiteLLM proxy: a streamed call whose stream flag lives only on the response's own `_hidden_params` is metered with `is_streamed: true`. The payload builder re-derived the hidden params from request metadata alone rather than using the ones the hook had already resolved, so exactly the fallback branch that exists for that case was ignored.

### Deprecated
- `revenium_middleware.litellm.proxy.middleware.MiddlewareHandler` — the `litellm_settings.callbacks` entry `proxy_handler_instance` — is deprecated in favour of `ReveniumGuardrail`. It meters but never enforces a budget. It keeps working in this release and emits one `DeprecationWarning` and one log line when the proxy builds it, naming the guardrail and the README's "Migrating from the callback". Enabling both would meter every call twice; as a safety net for a proxy mid-migration, a guardrail configured to run on every request (`default_on: true` with `post_call` among its modes) claims metering ownership and the callback stops submitting rows, logging once to say so. That net deliberately does not apply to a guardrail without `default_on`, without `post_call`, or with a per-tag `Mode` that selects hooks per request — such a guardrail may not run on a given request, and suppressing the callback could drop metering entirely (a per-tag configuration logs, at info, that it is not claiming ownership). Delete the callbacks entry rather than relying on the net.

### Fixed

The server keys its department maps by the normalized address (trimmed, lower-cased); the SDK looked the caller up with the address exactly as the application supplied it, so those calls reached the provider and spent the money, and the block only surfaced on the next call's response.

### Added
- An early warning before a department budget blocks you. The server publishes, with the enforcement rules, which people have crossed the warn tier of a per-person department (org-unit) cap without being blocked (`orgUnitBudgetWarnings`); the SDK now reads it and logs one warning naming the rule and — when the server publishes it — that person's own balance and the rule's threshold. Until now the first signal a developer got from the SDK was the hard block, while Slack, the webhook and the audit trail had all warned already. The line is emitted once per caller per refreshed verdict rather than once per call; a warning never blocks and never raises; a caller who is already blocked is not additionally warned; and a server that publishes no warnings map behaves exactly as before. The map is cached and persisted in the same rollback-safe, owner-only department snapshot as the block map, bound to the same rules fingerprint.

Entries are forwarded exactly as supplied, so `provenance`, `recordedBy` and `source` keep their documented server-side defaults instead of being misattributed client-side; the SDK shape-checks each entry (a non-blank `key`, a `value`) before any request and leaves the economics rules to the platform, which requires the metric to be declared `PER_JOB` on the job type and range-checks `quality_rate` to 0..1. Facts are what AI Alerts evaluate `QUALITY_RATE` from, so an integration that could not emit them was invisible to those rules. Appending facts does not advance the job's `entityVersion`, so a handle keeps the version it recorded and a following `amend_outcome()` still locks against it. The append is retried only on `429` and never on an ambiguous gateway error, because a repeated append records a second fact rather than the same one.

Set `usage_metadata={"agent_version": "1.4.2"}` (or `agentVersion`) to record which release of your agent produced a call, and cost breaks down per agent version. Accepted on completions, audio, image and video together, forwarded by every provider integration, and capped at 64 characters to match the ingest contract. This is the agent's own version and is distinct from `agentic_job_version`, which versions the agentic job definition; the two never overwrite each other.
- Job type economics: `upsert_job_type_economics`, `get_job_type_economics`, `report_period_facts`, `create_baseline` and `list_baselines` (with the `JobTypeEconomics`, `PeriodFactEntry` and `Baseline` models) declare a job type's metrics and economics, append period facts and versioned baselines. Appends (facts, baselines) are retried only on `429`, never on an ambiguous gateway error, because a repeated append records a second fact.

### Changed
- `JobContext.amend_outcome()` accepts `expected_entity_version=` (the optimistic lock, defaulting to the version recorded by the handle's last report or amendment and omitted when none is known), and `reason` is now optional: an API-key caller may omit it and the platform records an automated correction reason derived from the source. `reason` remains the first positional argument, and a blank string is still rejected client-side. A version that is not a non-negative integer (`3.5`, `-1`, `True`) is rejected before the request rather than truncated.

- Enforcement rule refresh honours the server's `Retry-After` in full up to 20 seconds per call and then gives up for that cycle instead of refetching; the refresh cooldown is capped at 300 seconds so one absurd header cannot freeze rule refreshes.

Set it per call via `usage_metadata={"ticket_id": "JIRA-123"}` or process-wide via `REVENIUM_TICKET_ID` to attribute AI cost to an individual ticket or issue.
- Tunable blocking behavior for outcome calls. Outcome reporting, amendment, and history retrieval are synchronous HTTP requests with retries; `retry_attempts`, `retry_initial_seconds`, and `retry_max_seconds` bound how long they may block, and are accepted by the `JobContext` constructor, `JobContext.attach()`, `get_outcome_history()`, and the CrewAI wrapper's outcome helpers.

### Changed
- The agentic outcomes API (reporting, amending, and reading job outcomes) requires a write-scope API key (`rev_sk_`). Metering keys (`rev_mk_`) meter completions and tool events only; the SDK now rejects them client-side with a clear error before any HTTP request is made, instead of surfacing a server-side authorization failure. Key resolution order is explicit `api_key=`, then `REVENIUM_OUTCOME_API_KEY`, then `REVENIUM_METERING_API_KEY`. The outcomes API base URL is configurable via `REVENIUM_PROFITSTREAM_BASE_URL`.
- Team resolution for outcome reporting follows explicit `team_id=`, then `REVENIUM_TEAM_ID`, then automatic resolution from the API key, raising `OutcomeReportingError` if none of those yields a team.

## [0.3.0] - 2026-07-17

### Added

Setting `REVENIUM_BEDROCK_TRANSPORT=1` meters raw `boto3.client("bedrock-runtime")` usage — `invoke_model`, `invoke_model_with_response_stream`, `converse`, and `converse_stream` — for Anthropic Claude models with no application code changes. ## [0.2.0] - 2026-07-09

### Added
- Store-and-forward buffering for metering events. Events that fail delivery with a transient error (connection failures, timeouts, rate limiting, or server errors) are no longer dropped: they are held in a bounded in-memory buffer and automatically replayed in the background once the backend is reachable again. Replayed events keep their original `Idempotency-Key`, so the backend safely deduplicates any overlap. The buffer is tunable via `REVENIUM_BUFFER_MAX_SIZE` (default 1000 events, oldest evicted first) and `REVENIUM_BUFFER_FLUSH_INTERVAL` (default 30 seconds); buffered events expire after 24 hours. A new `get_buffer_stats()` helper exposes buffer counters for observability, and a best-effort final drain runs at process exit.
- `initialize_metering(api_key=..., base_url=...)` for explicit programmatic (re)configuration of the metering client at runtime — useful for credential rotation or for configuring metering after import. Invalid keys raise immediately instead of failing silently.

### Changed
- Enforcement rule fetches now ride out transient failures (rate limits, server errors, connection errors) with exponential backoff capped at 8 seconds, honoring `Retry-After` headers. If retries are exhausted the SDK fails open and keeps the previously cached rules — an enforcement-refresh outage never blocks application traffic.
- Tool metering (`meter_tool` / `report_tool_call`) now dispatches events fire-and-forget on a background thread. Decorated functions and manual reporting return immediately instead of blocking on the metering network round-trip.

### Fixed
- Anthropic: raw streaming via `client.messages.create(stream=True)` is now metered. Previously only the `client.messages.stream()` context-manager path produced metering events.
- Streams abandoned before completion (early `break`, explicit `close()`, or garbage collection) now submit a metering event with the usage observed up to that point instead of silently dropping it. Applies to sync and async streams across providers.
- OpenAI streaming: when the middleware injects `stream_options={"include_usage": true}` to obtain token usage, the synthetic final usage chunk is no longer surfaced to callers that did not request it — the visible chunk sequence now matches the raw SDK exactly.
- Metering credentials set via environment variables after `revenium_middleware` is imported are now picked up on the next metering call; there is no longer an import-order requirement.
- Tool metering honors `configure()` overrides and environment variables at dispatch time and uses the correct metering API path.
- Anthropic on AWS Bedrock: the adapter now resolves the AWS region following boto3 conventions (client configuration, then `AWS_REGION`, then `AWS_DEFAULT_REGION`) instead of always defaulting to `us-east-1`.
- Anthropic on AWS Bedrock: genuine API errors from Bedrock calls now propagate to the caller instead of being masked by an internal fallback path.
- Streaming metering now reports `completion_start_time` as the arrival of the first stream event, improving time-to-first-token accuracy.
- DEBUG-level logging no longer leaks prompt or message content and credentials: sensitive fields (API keys, authorization headers, tokens) are redacted and message content is summarized across provider integrations.

## [0.1.7] - 2026-05-28

### Added
- HMAC webhook verification helper (`revenium_middleware.webhooks.verify_signature`) for verifying webhook payloads signed by Revenium. Supports secret rotation by accepting multiple secrets, multiple signatures per request (RFC 7230 multi-value headers), configurable timestamp tolerance, and case-insensitive hex comparison. README includes a FastAPI verification example.
- Automatic `Idempotency-Key` generation for AI metering submissions. Duplicate retries of the same metered event are now safely deduplicated by the Revenium backend without any caller-side work. Callers can still override the key explicitly via the new `idempotency_key` context manager when they need to control the value (for example, to tie metering to an upstream request id).

### Changed
- All provider integrations (OpenAI, Anthropic, Google, Ollama, LiteLLM, Perplexity, fal.ai) now submit metered AI events through a single shared `submit_ai_event` wrapper. This unifies idempotency-key handling across providers and makes future header-level changes a single-point edit.

### Security
- `verify_signature` now rejects empty-string secrets at the type guard. An empty secret would otherwise be used as a zero-byte HMAC key, which any caller could forge against trivially. Configuration mistakes that produce empty secrets now fail closed.

### Fixed
- `MeteringThread` now correctly propagates Python `contextvars` from the calling thread, so metadata set via `set_idempotency_key`, decorators, or context managers reaches the background metering worker reliably.
- `set_idempotency_key('')` and an empty `idempotency_key=` argument now raise `ValueError` instead of silently bypassing dedup. An `Idempotency-Key` passed through `extra_headers` is similarly rejected to avoid two competing sources of truth.
- The `Idempotency-Key` header guard in `submit_ai_event` is now case-insensitive, so callers passing alternate casings (e.g. `idempotency-key`) through `extra_headers` still hit the guard rather than silently shadowing the wrapper's value.
- Deprecated-field log warnings (`organizationId` / `productId` aliases) are now deduplicated per field pair so high-volume applications using legacy aliases no longer get a `logger.warning` flood on every call.
